A

核心观点：问题在于让模型别乱来

原文 1.1

一个会说话的概率分布，一旦能接触 shell、Git、网络和本地文件，问题就从“回答得不够好”变成了“执行造成实际破坏”。

Harness Engineering 就是一套制度化控制平面。它把这样一个不稳定的核心部件，约束成可管理的系统。它要面对的现实只有一条：模型并不天然值得信任。这个判断未必轻松，但通常有用；忽视它，问题最后多半会出现在日志和事故记录里。

Claude Code 的五层 Harness

Harness：约束执行的五层
  • 第一层：受约束的会话系统分层拼装的 prompt（B，第 2 章展开）
  • 第二层：持续循环带状态的 query loop（C，第 3、5 章展开）
  • 第三层：工具服从调度运行时决定并发还是串行（D，第 4 章展开）
  • 第四层：最危险的工具配最细的规矩Bash 的高密度约束（E，第 4 章展开）
  • 第五层：错误属于主路径失败按恢复路径处理（F，第 6 章展开）

B

第一层：受约束的会话系统

原文 1.2

表面上，Claude Code 像一个能对话、还能顺手改代码的 CLI。原文说，从实现上看，它一开始就没把自己当成“裸模型接口”。它是一个会话系统，有上下文边界、运行时状态和行为规约。这一点从 system prompt 的组织方式就能看出来，原文说它由三部分依次组成：

  1. 身份和总任务。
  2. 系统级说明：工具、权限、系统提醒、上下文压缩。
  3. 做任务时的工程约束：不越权改动，不把验证说成已完成，不为省事发明抽象。

很多人谈 prompt，还停在“你是一个什么样的助手”这种修辞层面。原文说，Claude Code 把 prompt 放进了运行时控制结构，用这些文字规定执行边界、失败行为和报告责任。

分段拼装

原文说，这个 prompt 是分段拼装的：静态部分和动态部分明确拆开，memory、language、output style、MCP instructions、scratchpad 等内容按段注入。系统再把默认 prompt、自定义 prompt、agent prompt 和追加 prompt 组织成一套优先级规则。

原文由此得出一个朴素的工程事实：可用的代理系统不能靠一段“万能提示词”解决所有问题。它必须把控制拆成层，把层拆成职责。否则，新增的提醒和禁令很快会互相冲突，系统行为也会难以预测。

事实核对
  • 源码位置（原文：src/constants/prompts.ts、src/utils/systemPrompt.ts）和 getSystemPrompt() 无法核对：源码不公开。
  • 三部分结构：在完整版 prompt 里属实（实测）。完整版依次是身份、“# System”（工具、权限模式、系统提醒、自动压缩旧消息）、“# Doing tasks”（例如 “Don't add features, refactor, or introduce abstractions beyond what the task requires”）。
  • 但文档说，较新的模型默认用一份更短的 prompt，“with abbreviated tool descriptions”；软件工程指令那一节 “only the full system prompt includes”。实测中，haiku 5.5 默认拿到的是短版：主块约 8,500 字符，而完整版约 29,700 字符。短版仍要求如实报告结果。
  • 动态段：文档有 --exclude-dynamic-system-prompt-sections，能把 auto memory 位置等每个用户不同的内容移出 system prompt，说明确实有动态段。实测中 memory 段在 system prompt 里；本次没配置 language、output style、MCP 服务器说明，这几段的位置没有观察到。scratchpad 是否进 system prompt，无法核对。
  • 优先级：文档写明 --system-prompt 替换默认 prompt，--append-system-prompt 追加到末尾，--agent 的代理 prompt “replaces the default Claude Code system prompt entirely”。实测与文档一致；--agent 和 --system-prompt 同时给时，用的是自定义文本，这一点文档没写。
C

第二层：代理依赖持续循环

原文 1.3

prompt 规定系统应该成为什么样子，query loop 规定它实际上怎样运行。原文说，Claude Code 的核心不在某个单独的 API 调用，而在 query() 和 queryLoop()。

（示意：按原文文字画。）

  • 跨迭代状态：messages、toolUseContext、autoCompactTracking、maxOutputTokensRecoveryCount、hasAttemptedReactiveCompact、pendingToolUseSummary、turnCount、transition 等，都放进同一个跨迭代状态。这等于正式承认：上一轮留下的问题会进入下一轮，系统必须有能力继续处理。
  • 调用前的治理：每轮调用模型前，先处理消息裁剪、tool result budget、history snip、microcompact、context collapse、autocompact。共同目的是在调用发生前，尽量把控制权收回到运行时一侧。

这是 Harness 思维的核心：系统能不能在连续多轮里保持行为一致。具体要看四点：

  • 有没有预算概念。
  • 有没有恢复概念。
  • 上下文膨胀后有没有自救机制。
  • 工具调用失败后，能不能继续推进任务。

缺少这些结构，所谓智能体只是一个不稳定的执行者。所以原文说，Harness Engineering 不是 prompt engineering 的附属品：

prompt engineering Harness Engineering
关心 措辞 状态机
决定 表达效果 系统行为最终由谁负责
事实核对
  • query()、queryLoop()、各状态字段和治理步骤的名字无法核对：源码不公开。第 3 章核对版逐项核对了这一层，这里只列结论。
  • 行为属实的部分：请求全部流式；回复结束后有 Stop hook，阻塞时再来一轮；手动压缩后，下一次请求从摘要开始；输出被截断后自动续写（第 3 章实测）。
  • 治理步骤里，自动压缩和工具结果上限有文档依据；history snip、microcompact、context collapse 在文档和 CHANGELOG 里查不到。
D

第三层：工具调用必须服从调度

原文 1.4

模型只能输出文本时，顶多让人觉得它有时说得太满。一旦能调用工具，风险就从修辞风险变成执行风险。这时最重要的问题是：谁决定工具怎么跑。原文说，Claude Code 的答案是：运行时根据工具属性决定并发还是串行。

（示意：按原文文字画，名字取自原文。）

原文说，这说明 Claude Code 没有把工具当成模型能力的自然延伸，而是当成需要调度纪律的受管执行单元。缺少调度纪律的工具系统，只会把模型的不稳定性放大到外部世界。不受约束的并发会扩大事故半径；Claude Code 在这里采取偏保守的策略，在会碰到文件、终端和权限的场景里，这种保守通常更可靠。

实测：只读工具并发，写工具排队

实测让模型在同一条回复里依次调用 Read、Read、Glob、Write、Write。每个工具的 PreToolUse hook 都故意睡 1.5 秒，这样能看出哪些工具同时在跑。时间以第一个 hook 开始为 0（实测，v2.1.312）：

  1. 0 s两个 Read 开始相隔 0.05 秒先后进入 hook
  2. +0.3 sGlob 开始与两个 Read 重叠
  3. +1.8 s三个只读工具都结束三段时间互相重叠
  4. +2.3 s第一个 Write 开始只读工具全部结束后才开始
  5. +4.2 s第二个 Write 开始第一个 Write 结束后才开始
  6. +5.9 s第二个 Write 结束下一次请求按原顺序带回 5 个 tool_result
事实核对
  • runTools()、partitionToolCalls()、isConcurrencySafe() 和原文给出的文件位置无法核对：源码不公开。文档没有写工具怎样并发。
  • “按工具属性决定并发还是串行”行为属实（实测）：三个只读工具同时在跑，两个 Write 一个接一个执行。
  • 下一次请求里，5 个 tool_result 的顺序与调用顺序相同，但这次完成顺序也与调用顺序相同。第 4 章核对版另做了两次实测：完成顺序不同时，tool_result 按完成先后排列。context modifier 本身从外部看不到，无法核对。
  • 局限：只做了一次，只覆盖这几种工具。
E

第四层：最危险的工具配最细的规矩

原文 1.5

所有工具里，Bash 最值得警惕。它几乎不受领域边界约束，能直接接触文件、进程、网络和 Git 仓库，还带着重定向、管道等复杂的 shell 语义。系统对 Bash 过度信任，后果通常会很具体。

原文说，BashTool 的 prompt 里写了一整段操作规约，尤其是 git 和 PR 部分。下表逐条对照实测抓到的两版 Bash 工具说明：

原文列出的规矩 完整版 prompt 短版 prompt（较新模型默认）
不要乱改 git config ✓“NEVER update the git config” ✗没有
不要跳过 hooks ✓“Never skip hooks (--no-verify)” ✗没有
不要随手 git add . ✓优先按文件名添加，不用 “git add -A” 或 “git add .” ✗没有
pre-commit 失败后，不要用 --amend 把上一条提交也搭进去 ✓写明 pre-commit 失败时提交没有发生，--amend 会改到上一条提交 ✗没有
没有明确要求时，不要提交 ✓“NEVER commit changes unless the user explicitly asks you to” ✓“Commit or push only when the user asks”
更不要默认 push ✓“DO NOT push to the remote repository unless the user explicitly asks” ✓同上一句

有人会觉得这过于细碎，但高风险接口通常就需要高密度约束。Bash 一旦进入真实工作流，很多规则都必须明确写出来。

原文由此提出 Harness Engineering 的一条重要原则：把高风险能力包装成高约束能力，能力越强，控制越细。外部世界不会因为模型语气坚定，就原谅一次错误执行。

事实核对
  • 原文的文件位置 src/tools/BashTool/prompt.ts 无法核对：源码不公开。
  • 原文列出的六条规矩，在完整版 prompt 的 Bash 说明里都有（实测）。完整版的 Bash 说明约 10,700 字符。
  • 短版只有约 2,100 字符，git 部分只剩“用户要求时才提交或推送”。文档也说短版是 “abbreviated tool descriptions”。所以“高密度约束”在完整版里成立；在较新模型默认的短版里，密度低得多。
  • 文档另有一个开关：includeGitInstructions 设为 false 时，会去掉内置的提交和 PR 说明。
F

第五层：错误属于主路径

原文 1.6

很多软件把成功路径当正文，把失败路径当例外。原文说，代理系统不能这样，因为它的失败并非偶发，而是一直存在：

代理系统会持续遇到的失败
  • 上下文类超 token、prompt too long、max_output_tokens
  • 执行类工具被拒绝、hook 阻塞、API 重试
  • 交互类用户打断

（分类是本页归纳，条目来自原文。）

这些情况如果只在最后用几个 catch 打发，系统表面在运行，实际只是不断把麻烦往后推。原文说，Claude Code 的 query loop 没这样做。看 autocompact 怎样处理、上下文上限和阻断逻辑怎样注释，就能看出它把失败当成结构性条件，会持续发生。

普通助手 Harness
设计逻辑 先回答，错了再道歉 先约束，再执行
出错时 靠临场发挥补救 按恢复路径处理

会道歉的系统不一定成熟。更成熟的系统知道四件事：何时不该开始、何时该重试、何时该中止、何时该准确汇报失败。

事实核对
  • 原文引用的 autocompact 代码和注释无法核对：源码不公开。
  • 原文列的失败类型都有文档或实测依据。文档 errors 页逐项写了 prompt 太长、输出超过上限、自动重试的处理；工具被拒绝、用户中断后，被打断的调用会拿到一条错误结果（第 3 章观察）；Stop hook 阻塞后会再来一轮（第 3 章实测）。
  • 上下文上限的阻断：交互界面会显示 “Context limit reached · /compact or /clear to continue”（文档）。

从源码提炼的第一个原则

原文 1.7
第一个原则

代理系统的关键能力是约束执行。

原文说，源码在五个关键位置指向同一个结论。源码不公开，下表把原文的证据换成核对后的依据：

原文的源码依据 说明什么 核对后的依据 详见
constants/prompts.ts prompt 是控制平面的一部分，而不是人格装饰 完整版 prompt 里有工具、权限、压缩说明和工程约束（实测）；较新模型默认的短版更简略（文档、实测） B
utils/systemPrompt.ts 系统行为必须有清楚的分层优先级 自定义、代理、追加三种 prompt 的优先级（文档、实测） B
query.ts 代理运行依赖持续的循环状态，而不是单次问答 流式循环、Stop hook 再来一轮、压缩后从摘要继续（第 3 章实测） C
services/tools/toolOrchestration.ts 工具调用必须服从调度纪律 只读工具并发、写工具排队（实测） D
tools/BashTool/prompt.ts 高风险工具必须伴随高密度约束 完整版 Bash 说明里有原文列的六条规矩；短版只剩一条（实测） E

放在一起看，Harness Engineering 并不神秘。原文说，它只是坚持几条常被忽视的工程常识：

  • 模型会犯错。
  • 工具会扩大错误后果。
  • 上下文会膨胀。
  • 状态会污染下一轮。
  • 用户会打断你。
  • 失败会反复出现。

原文提炼的工程原则：既然如此，系统就不能靠“聪明”维持秩序，只能靠结构维持秩序。结构不像聪明那样显眼，但通常更可靠。核对后，五处证据都能换成文档或实测依据，论点成立。需要补充的是：较新模型默认用短版 prompt，很多约束写得更简略。约束密度随 prompt 版本而变。

下一章讨论这套结构里最容易被误解的一层：system prompt。很多人把它看成人设文本，第 2 章会说明它更接近规章制度：人设可以改善观感，规章才能约束机器。
