《Harness Engineering：Claude Code 设计指南》第 7 章解读，已按官方文档、本机观察和实测核对

原文：第 7 章 多代理与验证：用分工和验证管理不稳定性

一句话结论：原文认为，多代理的价值不在并发，而在给不确定性分区。fork 先保住缓存和状态边界；子代理默认隔离；综合不能外包；验证要和实现分开；子代理的生命周期要可观测、可中止、可清理。

核对后，论点大体成立。在 v2.1.312 上实测到下面几件事：

  • fork 子代理的请求与父请求前缀相同，第一次请求直接读到父代理的缓存。
  • 普通子代理和父代理互不共享“读过哪些文件”；fork 继承父代理的记录。
  • SubagentStart、SubagentStop 两个 hook 都会触发；SubagentStop 用 exit 2 能让子代理继续工作。
  • 父代理被中断时，子代理和它启动的后台命令都被停掉。

源码文件、函数名和字段名无法核对。

需要修正四点：

  • 原文说子代理的文件读取状态从父代理复制而来。实测只有 fork 如此；普通子代理从空状态开始，文档也这样写。
  • 原文的不变式说，SubagentStart 之后一定有 SubagentStop。实测父代理被中断时，SubagentStop 没有触发。
  • 原文说子代理被包装成不弹权限确认。文档说普通子代理的权限确认会转给用户。
  • 原文引用的 coordinator 模式（Always synthesize、不要 rubber-stamp 等），文档、CHANGELOG 和本机抓到的 prompt 里都查不到，无法核对。Agent 工具的说明里有相近的要求。

核对依据：Claude Code 官方文档 code.claude.com/docs（2026-10-30 查阅）；anthropics/claude-code 仓库的 CHANGELOG（最新条目 2.1.312）；本机 Claude Code 2.1.312 的实测和抓包。依据分四种标签：文档、观察、实测（v2.1.312）、旁证（CHANGELOG）。逐条结果见附录。

A

单代理走到一定程度，问题就变成怎么分工

原文 7.1

原文说，单代理的小矛盾常靠耐心遮过去。任务一大，研究、实现、验证就挤在同一条上下文链上，抢预算、抢注意力、抢叙事中心。

多代理看上去是自然答案，实际并不便宜：不加约束的并行，只会把单代理的混乱复制几份。原文说，真正困难的是两件事：隔离各个 agent 的不稳定性，再把结果组织回来。

原文说，Claude Code 的源码在这点上很清醒。它没有把 subagent 当成“另一个会说话的窗口”，而是当成一段受管的执行流程。这段流程要有明确的缓存边界、状态边界、验证职责和清理责任。

本章讲的四类边界（本页归纳）
  • 缓存边界fork 必须与父请求共享缓存相关参数（B）
  • 状态边界子代理默认隔离可变状态（C）
  • 职责边界协调者负责综合，验证独立成阶段（D、E）
  • 生命周期启动、停止、中止、清理都要可管理（F）

本节是原文的观点，不涉及需要核对的事实。

B

forked agent 的第一原则是 cache-safe

原文 7.2

原文说，src/utils/forkedAgent.ts 开头有一段注释，说明了 forked agent 工具的四项职责：

  • 与父代理共享 cache-critical params，确保 prompt cache 命中。
  • 跟踪整个 query loop 的 usage。
  • 记录指标。
  • 隔离可变状态，防止干扰主循环。

最先出现的是“共享 cache-critical params”。原文认为这并非偶然：fork 是运行时层面的受控分叉，必须在意哪些参数要和父请求一致。不一致，prompt cache 就无法共享，成本和延迟立刻变坏。

原文说，CacheSafeParams 列出了这些要素：systemPrompt、userContext、systemContext、toolUseContext、forkContextMessages。源码还专门提醒：不要随便改 maxOutputTokens，因为它会影响 thinking 配置，而 thinking 配置是 cache key 的一部分。

原文由此认为，多代理首先是运行时经济学问题。子代理每次都把父上下文重新烧一遍 token，看上去在并行提效，实际只是把浪费并行化。

原文的骨架：forkAgent() 做了什么

原文给了一段伪代码骨架，来源标为 forkedAgent.ts 和 createSubagentContext.ts。本页按步骤转述：

  1. 组装 CacheSafeParams，要求与父代理一致。
  2. 建子上下文：复制父代理的文件读取状态；新建一个挂在父代理上的子中止控制器；包装读状态的接口，不弹权限确认；写状态的接口默认不做事；嵌套记忆相关的集合重新建。
  3. 只有显式 opt-in 时，才共享父代理的中止控制器或写状态接口。
  4. 触发 SubagentStart hook，开始跟踪 usage。
  5. 结束时一定触发 SubagentStop hook，带上子代理的转录路径。

实测：fork 的请求和父请求比一比

实测让父代理调用 Agent 工具，subagent_type 设为 fork，再把抓到的请求逐项比较：

请求里的项目 fork 的第一次请求 普通子代理（general-purpose）的第一次请求
system prompt ✓与父请求相同，只有计费头多了 cc_is_subagent=true ✗换成子代理自己的 prompt
工具定义 ✓与父请求相同（14 个） ✗不同（12 个）
模型、max_tokens、thinking 配置 ✓与父请求相同 —
消息 父代理的全部历史，加这次 Agent 调用、一个占位结果和一段 fork 指令 只有委派的任务消息
缓存 ✓读到 24,616 token，正好是父请求写入的量 读的是子代理自己的缓存

fork 指令开头写着 “You are a worker fork. The transcript above is the parent's history — inherited reference, not your situation.”

事实核对
  • forkedAgent.ts、CacheSafeParams、createSubagentContext() 和注释原文无法核对：源码不公开。
  • fork 共享缓存属实（文档、实测）。sub-agents 文档的对比表写着 fork 的 prompt cache “Shared with main session”，普通子代理是 “Separate cache”。实测见上表。
  • 缓存相关参数保持一致属实（实测），命名无法核对。实测中 fork 的 system prompt、工具、模型、max_tokens 和 thinking 配置都与父请求相同。
  • 这条原则只适用于 fork。普通子代理用自己的 system prompt 和工具，文档写明它的第一次请求 “doesn't read the parent's cache”。
  • 跟踪 usage 属实（观察）：stream-json 输出里，子代理的进度消息带 total_tokens 和 tool_uses。
  • 压缩用的也是同一套前缀共享（文档、观察）。prompt-caching 文档写到压缩请求 “uses the same prefix-sharing approach”，第 6 章抓到的摘要请求也沿用主会话的 system prompt 和工具。

C

状态隔离：子代理首先要减少污染

原文 7.3

原文说，forked agent 的第二个关键在 createSubagentContext()。源码写得很直白：默认所有可变状态都隔离，避免干扰父代理。它默认做这些事：

  • 复制文件读取状态（readFileState）。
  • 生成子中止控制器，不直接共享父代理的。
  • 包装读状态的接口，让子代理避免权限确认。
  • 写状态的接口默认不做事。
  • 嵌套记忆相关的集合都重新建。

原文说，只有明确 opt-in 时，才共享某些回调，例如 shareSetAppState、shareSetResponseLength、shareAbortController。

原文认为，子代理最宝贵的地方，是不把自己的局部混乱污染主线程。研究中出现误判，临时读到文件，推理走了一次性分支，工具决策做到一半。这些全写回主上下文，主上下文只会更快变脏。原文说，Claude Code 的态度是：共享要靠明确同意，隔离才是默认。这更像数据库事务设计，不像聊天玩具。

实测：子代理和父代理共享“读过的文件”吗

Edit 工具要求先读过文件，才能修改。新模型可以跳过这一步，所以这组实验改用必须先读的 Haiku 4.5：

实验 谁读了 a.txt 谁直接 Edit 结果
对照 没人读 父代理 ✗报 “File has not been read yet. Read it first before writing to it.”
子读父改 普通子代理 父代理 ✗同样报错：子代理读过，不算父代理读过
父读子改 父代理 普通子代理 ✗同样报错：父代理读过，普通子代理不继承
父读 fork 改 父代理 fork ✓修改成功：fork 继承了父代理的读取记录
事实核对
  • createSubagentContext()、readFileState、setAppState、各个 share 开关的名字无法核对：源码不公开。
  • 隔离属实（实测）：子代理读过的文件，父代理不能直接改。
  • “复制父代理的读取状态”只对 fork 成立（实测）。普通子代理从空状态开始。文档也写到，子代理 “doesn't see your conversation history, the skills you've already invoked, or the files Claude has already read”；fork 例外。原文这一节讲的是 forked agent，所以原文的说法在 fork 上成立。
  • “避免权限确认”与文档不一致。文档说，前台子代理的权限确认 “are passed through to you”；后台子代理的权限确认也会出现在主会话里。内部使用的 forked agent 是否不弹确认，无法核对。
  • 中止控制器挂在父代理上属实（实测，见 F 节）。
  • 实验用的是 Haiku 4.5；文档写到，新模型在不需要权限确认时可以编辑没读过的文件，所以用新模型测不出这一点。
D

协调者模式：综合才是稀缺能力

原文 7.4

原文说，src/coordinator/coordinatorMode.ts 对协调者的要求很有分寸。协调者的工作包括：

  • 帮用户达成目标。
  • 指挥 worker 做研究、实现和验证。
  • 综合结果，并和用户沟通。
  • 能直接回答的问题就直接回答，不要滥委派。

原文说，最关键的一句在第 5 节 prompt 里：Always synthesize。worker 回报研究结果后，协调者必须先读懂，再写出具体的下一步 prompt。不要写 “based on your findings”，不要把理解继续外包给 worker。

原文认为，这是多代理的命门。稀缺的不是并行输出。稀缺在于有人把 worker 带回的局部知识重新压缩，写成清晰、可执行、可验证的下一步。缺这一层，多代理很快退化成礼貌的任务转发机。原文说，后续 prompt 必须写出具体文件、具体位置、具体变更：研究可以分布式，理解必须重新收束。

事实核对
  • coordinatorMode.ts 和协调者 prompt 原文无法核对：源码不公开。文档和 CHANGELOG 都没有 coordinator 模式（CHANGELOG 里的 coordinator 指 /claude-api 技能生成的 Managed Agents 结构，与此无关）。本机抓到的 system prompt 和工具说明里，也没有 “Always synthesize”“based on your findings” 这些句子。
  • 相近的要求有观察依据。本机抓到的 Agent 工具说明写着：父代理 “see only the summary it sends back”；委派时要把目标和已排除的可能写清楚；“if you cannot write a clear one, you do not understand the task well enough to hand it off”；子代理的报告用户看不到，要由父代理转述。
  • 由主会话综合结果，有文档依据。sub-agents 文档的并行研究模式写着 “then Claude synthesizes the findings”；agent-teams 文档说 lead 负责 “synthesizing results”。
E

验证必须独立成阶段

原文 7.5

原文说，coordinatorMode.ts 把常见任务分成四类：Research、Synthesis、Implementation、Verification。它特别强调，验证的目标是证明代码有效，而不只是确认代码存在。原文引了四句：

  • run tests with the feature enabled
  • investigate errors, don't dismiss as unrelated
  • be skeptical
  • test independently, don't rubber-stamp

原文说，这说明 Claude Code 把验证当成第二道质量关，而不是实现 worker 顺手带的动作：实现 worker 自证，验证作为独立 QA。

原文认为，“我改了代码”和“代码因此正确”之间隔着一条很宽的河，模型尤其擅长在上面搭纸桥。它会给出改动、解释，甚至像样的测试输出，但这些都不等于功能真的站住了。把验证单列，是为了防止“会改代码”冒充“能交付结果”。

事实核对
  • 四类任务和四句验证要求无法核对：出处同 D 节，文档和本机 prompt 里都查不到。文档列出的内置子代理是 Explore、Plan、general-purpose 等，没有专门的验证子代理。
  • 相近的要求有观察依据。本机抓到的 Agent 工具说明写着：子代理的错误 “come back in the same confident register as its findings”；“an agent handed your hypothesis tends to return it confirmed”；需要独立复核时，“give it the code, not your conclusion”。这些句子支持原文“验证要独立”的论点，但不是原文引的那段 prompt。
F

hooks 和任务生命周期：子代理不是扔出去就算了

原文 7.6

原文说，多代理系统有个容易被忽略的地方：spawn 只是开头，收尾同样重要。

原文说，src/utils/hooks/hooksConfigManager.ts 定义了两类 hook：

  • SubagentStart：子代理启动时触发，输入里有 agent_id 和 agent_type。
  • SubagentStop：子代理即将结束时触发，输入里还有 agent_transcript_path。hook 以 exit code 2 退出时，stderr 会反馈给子代理，让它继续跑。

原文说，这说明子代理是显式暴露生命周期节点的系统对象。启动时可以观测，停止前可以介入，转录路径可以追踪。

原文说，src/tasks/LocalAgentTask/LocalAgentTask.tsx 的 registerAsyncAgent() 展示了另一个层面。每个异步 agent 都注册 cleanup handler，父代理中止会自动传给子代理的中止控制器。任务结束后，还要清掉输出、更新状态、解除 cleanup 注册。原文认为这很像操作系统，它关心四个问题：

  • 这个 agent 是否仍在运行。
  • 父任务死了，它是否该跟着死。
  • 它的输出文件是否还要保留。
  • 它的 cleanup 回调有没有泄漏。

原文说，很多多代理 demo 只做到“能再起一个 agent”。Claude Code 多做了一步：把 agent 当作会泄漏资源、会残留状态、会在父进程结束后变成孤儿的运行实体。

实测：hook 和中断

实验 实测到的过程
正常委派 先触发 SubagentStart（带 agent_id、agent_type），子代理内的工具调用也触发 PreToolUse，hook 输入里带 agent_id。结束时触发 SubagentStop，agent_transcript_path 指向的文件存在
SubagentStop 第一次以 exit 2 退出 子代理收到 stderr 里的话，又回答了一轮；第二次 SubagentStop 的 stop_hook_active 为 true。父代理拿到第二轮回答
子代理运行后台命令时中断父代理 子代理和它的后台命令都被标为 killed；父代理的 Agent 调用拿到一条 is_error 的结果，随后是 “[Request interrupted by user for tool use]”。SubagentStop 没有触发
事实核对
  • hooksConfigManager.ts、LocalAgentTask.tsx、registerAsyncAgent() 无法核对：源码不公开。
  • SubagentStart 和 SubagentStop 的输入字段属实（文档、实测）。hooks 文档列出的字段与原文一致；SubagentStop 还有 last_assistant_message。文档说 SubagentStart 不能阻止子代理启动，但可以注入上下文。
  • exit 2 让子代理继续属实（文档、实测）。文档写到：exit 2 时 stderr 里的话会交给子代理，decision: "block" 带的 reason 也一样。
  • 父代理中止时子代理跟着停属实（实测）。文档还写到，前台子代理启动的后台命令，在子代理结束、失败或被中断时一并结束。
  • “生命周期必须闭合”与实测不符：被中断的子代理没有触发 SubagentStop。Stop hook 的文档也写着用户中断时不运行。
  • 清理有文档依据：后台任务在 Claude Code 退出时自动清理；后台子代理成功结束后，面板里它那一行立即移除。清掉输出、解除注册这些内部步骤无法核对。

原文的图：多代理运行时生命周期

原文在这里放了一张图，标题是 “Multi-Agent Runtime Lifecycle - Spawn, Isolate, Reap”。图的意思是：

  • 父代理决定委派，确定 agent 类型和执行方式。
  • 本地或 worktree 方式进入子运行时：构建隔离的子上下文，运行子 query loop，跟踪进度、收集输出。remote 方式变成远程任务，返回句柄。
  • 子代理完成，就交给协调者综合；中止或出错，就传播失败或取消。
  • 最后统一清理，注销跟踪。

图上有两条注释。一条写着：隔离包括复制文件状态、子中止控制器、隔离可变集合、共享 cache-safe 参数。另一条写着：研究可以委派，理解不能；协调者负责综合。

事实核对
  • 执行方式属实（观察）。本机抓到的 Agent 工具参数里，isolation 可选 worktree 或 remote；remote “always runs in background”。另有前台、后台之分，默认后台，原图没有画。
  • 原图注释说隔离包括“复制的文件状态”和“共享的 cache-safe 参数”。实测这两项只适用于 fork；普通子代理是新上下文，有自己的 prompt 和缓存。本页补上 fork 分支。
  • 本页补上两个 hook：启动时触发 SubagentStart；完成时触发 SubagentStop，exit 2 或 block 会让子代理继续。
