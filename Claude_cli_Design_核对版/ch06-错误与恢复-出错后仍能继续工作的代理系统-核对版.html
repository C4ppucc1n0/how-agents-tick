核对后，论点成立。在 v2.1.312 上，用本机故障注入代理实测到下面几件事：

  • prompt too long 先被扣下，Claude Code 自动压缩后重试，用户看不到这个错误。
  • 压缩救不回来时才报错，并改跑 StopFailure hook，不跑 Stop hook。
  • 摘要请求自己超长时，Claude Code 截掉最早的一轮再试。
  • 529 过载按指数退避重试 10 次。

源码文件、函数名和状态字段无法核对。

需要修正四点：

  • 原文说 reactive compact 每回合只做一次。实测一个回合里压缩了两次，第二次保留得更少；CHANGELOG 2.1.284 写了这个改动。
  • 原文说输出截断时先提高 token 上限再重跑。这一步本机没观察到；默认请求的上限已是 128000。
  • 原文说恢复第一步是提交 context collapse 积压。文档和 CHANGELOG 都查不到 collapse，无法核对。文档写了另一个便宜的第一步：输入加 max_tokens 超限时，先减小 max_tokens 重试。
  • 原文说自动压缩连续失败 3 次后熔断。CHANGELOG 2.1.76 写了这个熔断，但本机实测没观察到：连续 8 轮压缩失败，每轮仍重新尝试。

A

核心观点：不要只写“正常情况下”

原文 6.1

很多设计文档只讲“正常情况下”，仿佛主路径漂亮，错误就会退场。原文说，代理系统一进入真实环境，这种写法就会露馅：

  • 模型会被截断，请求会超长。
  • hook 会制造回环，工具会中断。
  • fallback 会发生，恢复逻辑本身也会失手。

原文的判断标准是：成熟的代理系统，不看它顺畅时多像人，要看它出故障时像不像系统。原文说，Claude Code 的源码反复体现一个冷静判断：错误属于主路径，恢复是提前设计好的运行机制。

本章讲的恢复机制（本页归纳）
  • 单次错误怎么救
    • prompt too long扣下错误，分层恢复（B）
    • 恢复防回环只压缩有限次，跳过 Stop hook（C）
    • 输出截断续写，不 recap（D）
  • 恢复机制本身怎么管
    • 自动压缩熔断连续失败就停（E）
    • 压缩请求自己超长截掉最早的历史再试（F）
  • 收尾
    • 中断补齐 tool_result，压缩中断不算成功（G）
    • 执行叙事记录走过的恢复路径（H）

本节是原文的观点，不涉及需要核对的事实。

B

prompt too long：先扣下，再分层恢复

原文 6.2

原文说，对长会话代理来说，prompt too long 迟早会来。把它当偶发异常，系统迟早会被它教育。

原文说，query.ts 在流式阶段会识别三类可恢复错误，先“暂时扣下”，不立刻抛给用户：

  • prompt too long
  • media size error
  • max output tokens

意思是：有些错误先交给恢复系统试着处理，再决定是否展示。用户真正关心的，是系统还能不能继续干活。

在 prompt too long 这条路上，原文说恢复分两层：

  1. 启用了 context collapse 时，先调用 recoverFromOverflow()，提交已经 staged 的 collapse。
  2. 还不行，再调用 reactiveCompact.tryReactiveCompact()，做全文压缩。

原文说，好的恢复系统不会把所有错误都交给最重的一把锤子。它先保住最细粒度的上下文，必要时才接受更粗的摘要。

实测：注入一次 prompt too long

实测用本机代理拦截发往模型的请求，让第一次主请求返回 400 prompt too long。会话里已有两轮对话。下图是实测到的过程：

被拒后约 0.2 秒，摘要请求就发出了；整个过程中，-p 的输出里没有出现这个错误。

事实核对
  • query.ts、recoverFromOverflow()、reactiveCompact.tryReactiveCompact() 和“withheld”这个说法，都无法核对：源码不公开。
  • 先扣下 prompt too long 属实（实测）：注入一次后，最终结果是正常回答，is_error 为 false。
  • 被拒后自动压缩属实（文档、实测）。文档写到压缩 “normally summarizes your oldest exchanges and keeps the newest”，实测一致。
  • 恢复分层：先提交 collapse 积压这一步无法核对，文档和 CHANGELOG 都查不到 context collapse。文档写了另一个便宜的第一步：输入加 max_tokens 超过上限时，先减小 max_tokens 重试；减不动了才改为压缩。
  • 输出超长也会先尝试恢复（实测，见 D 节）。media size：文档写到 API 拒收图片时，Claude Code 移除这张图并提示 “could not be processed and was removed”。本次没有注入这类错误。
  • 文档还写了一种不压缩的情况：只有一轮对话时没有可摘要的内容，Claude Code 直接报错并说明原因。实测的报错与文档原句一致。
C

恢复不能把自己逼进死循环

原文 6.3

原文说，很多系统做恢复时会犯一个常见错误：一发现错误可恢复，就不停重试，把偶发事件升级成资源灾难。原文认为 query.ts 里有两处防护。

第一处：hasAttemptedReactiveCompact。 原文说，reactive compact 试过一次后，再遇到同类问题就不再重来。压缩之后还不行，再压缩一次多半只是换个姿势重演同一种失败。

第二处：跳过 stop hooks。 原文说，源码注释写得很直白：prompt too long 之后还让 stop hooks 介入，就可能出现 death spiral：

原文说，这句注释承认了最危险的错误：失败分支和恢复分支彼此咬住，开始无限自我复制。所以 prompt too long 无法恢复时，Claude Code 直接报错，并跳过 stop hooks。

实测：每次主请求都返回 prompt too long

实测做了两组，每次主请求都返回 prompt too long：

  • 第一组：直接提问。
  • 第二组：先让 Stop hook 阻塞一次，迫使系统再来一轮，再注入错误。
步骤 直接提问 Stop hook 先阻塞一次
第一次被拒 压缩，摘要约 2.6 万 token 的上下文 同左
第二次被拒 再压缩一次，这次保留更少 同左
第三次被拒 报 “Prompt is too long”，回合结束 同左
结束时的 hook StopFailure（error 为 invalid_request），不跑 Stop StopFailure；Stop 没有再运行
会话记录 两条 compact_boundary，最后一条是合成的错误消息 同左，另有一条 Stop hook 反馈

两组都在三次请求、两次压缩后停下，没有出现循环。

事实核对
  • hasAttemptedReactiveCompact 这个名字和源码注释无法核对：源码不公开。
  • “只压缩一次”与现状不符（实测、旁证）。实测一个回合里压缩了两次。CHANGELOG 2.1.284 写到，压缩后请求仍然太长时，“Claude Code now compacts once more, keeping less of the recent conversation”。论点“恢复要有次数上限”仍成立：第三次被拒就报错。
  • 报错并跳过 stop hooks 属实（文档、实测）。hooks 文档写到，Stop 在 API 出错时不运行，“API errors fire StopFailure instead”。实测两组都是这样，Stop hook 先阻塞过一次也一样。
  • 旁证：CHANGELOG 2.1.274 修了一个问题。由 hook 驱动的会话，reactive compaction 之后上下文再次溢出时，直接以 “Prompt is too long” 结束，没有再压缩。可见“hook 驱动续跑”和“压缩后再溢出”这个组合确实被单独处理过。
  • 文档还写了一种保护：Stop hook 连续阻塞 8 次后不再接受阻塞（CLAUDE_CODE_STOP_HOOK_BLOCK_CAP）。
D

输出被截断：先续写，不寒暄

原文 6.4

原文说，很多大模型产品有个坏习惯：输出一被截断，就先来一段客气话，“抱歉，刚才被截断了，我来总结一下”。态度不错，对工作几乎没帮助。

原文说，Claude Code 分两层恢复：

  1. 先提高上限。 当前用的是较保守的上限时，把 maxOutputTokensOverride 提到更高，直接重跑同一请求。这一步不插入 meta 消息，也不让模型先寒暄。
  2. 再要求续写。 更高的上限也不够时，追加一条 meta user 消息，大意是：直接继续，不道歉，不 recap；断在半句就从半句接着写；剩余工作拆小一点。

原文说，这条指令的目标是保持任务连续性，不把 token 花在礼貌性收尾上。每一次截断后的 recap 都会消耗预算，还会增加语义漂移。最后系统做的不再是任务本身，而是一轮轮地回顾自己做任务。

事实核对
  • 原文给的位置（src/query.ts:1185 往后）和 maxOutputTokensOverride 无法核对：源码不公开。
  • 续写属实（实测，见第 3 章）。把上限设成 400 后，回复两次被截断。Claude Code 每次追加同一条用户消息：“Output token limit hit. Resume directly — no apology, no recap of what you were doing. Pick up mid-thought if that is where the cut happened. Break remaining work into smaller pieces.” 第三次回复正常结束。消息内容与原文转述一致。
  • 旁证：CHANGELOG 2.1.0 写到，输出因 token 上限被截断时，Claude 会自动继续，不再显示错误。
  • “先提高上限”本机没观察到。用环境变量设上限时，三次请求的上限都是 400。默认配置下请求的上限已是 128000（claude-haiku-5-5），要很长的输出才能测，本次没做。
  • 文档只写了最终报错 “Claude's response exceeded the … output token maximum”，以及手动回复 continue。hooks 文档的 StopFailure 错误类型里有 max_output_tokens，说明续写也有用尽的时候。
E

自动压缩的熔断：恢复系统自己也要受治理

原文 6.5

前面讲的是单次错误怎么救。原文说，autoCompact.ts 处理的是另一层问题：恢复机制本身不断失败时怎么办。答案是：别一直试。

原文说，AutoCompactTrackingState 里有 consecutiveFailures。连续失败超过阈值后，即使 shouldAutoCompact 判断该压缩了，系统也直接跳过。源码注释给过数据：曾有大量会话在连续失败的自动压缩上，白白烧掉海量 API 调用，所以必须加熔断。

原文说，熔断的本质是承认当前恢复手段已经失效。不会收手的恢复系统，和不会刹车的汽车差不多。原文由此抽出一条原则：任何自动恢复机制都必须可计数、可限次、可熔断。否则，恢复会从保险丝变成新的起火点。

实测：让自动压缩每次都失败

实测把自动压缩的触发线调低到约 1 万 token，让每一轮开始前都触发自动压缩，再让所有摘要请求返回 400。同一个进程里连续发 8 条消息，每条等上一轮结束再发。

轮次 自动压缩 这一轮的摘要请求 之后
第 1–2 轮 尝试，失败 6 个 主请求照常发出，正常回答
第 3–8 轮 尝试，失败 4 个 同上
对照：不注入错误，6 轮 每轮都成功 每轮 1 个 正常回答

8 轮里每一轮都重新尝试自动压缩，没有在连续失败 3 次后停下。一次尝试会发几个请求：同一请求重试，再换两种变体。都失败后，这一轮不再压缩。压缩失败不影响本轮回答：主请求带着没压缩的上下文照常发出。

F

compact 自己也会爆：修复动作也需要修复策略

原文 6.6

原文说，compactConversation() 有一个现实主义的时刻：它承认摘要请求自己也可能 prompt too long。系统为了缩短上下文去发摘要请求，结果摘要请求也因为太长而失败。工程系统首先要解决的是继续运行，不是保持表面完整。

原文说，compact.ts 为此引入了 truncateHeadForPTLRetry()。摘要请求太长时，系统先把最早的 API round 成组地从头部剥掉，再重试压缩。这样用户不会卡在“连压缩都压不动”的状态里。

原文说，这种修复有损，会丢历史，但它优先保证用户不被完全锁死。源码注释称之为 last-resort escape hatch。原文的判断是：系统快要窒息时，先恢复呼吸，再讨论信息保真度。

实测：让摘要请求也返回 prompt too long

注入方式 实测到的过程 结果
主请求和第一次摘要请求各失败一次（做了 2 次） 摘要请求被拒后立即重试。重试请求的开头换成一条占位消息 “[earlier conversation truncated for compaction retry]”，最早的一轮被丢掉 ✓压缩成功，回合正常结束。摘要只剩故事标题，模型说无法概括情节
主请求失败一次，摘要请求一直失败 截掉最早一轮重试一次；仍被拒，就不再重试 报 “Prompt is too long”，回合结束

两次重复实验里，StopFailure hook 都在摘要请求第一次被拒后触发了一次，回合随后又正常结束，Stop hook 也运行了。E 节的实验也一样：每轮自动压缩失败后都触发一次 StopFailure。所以 StopFailure 触发时，回合不一定已经失败。

事实核对
  • compactConversation()、compact.ts、truncateHeadForPTLRetry() 和注释原话无法核对：源码不公开。
  • 截掉头部再重试属实（实测），命名无法核对。实测只看到一次截头重试；历史更长时会不会多截几轮，本次没测。
  • 旁证：CHANGELOG 2.1.85 修了一个问题：对话太长、摘要请求自己都放不下时，/compact 失败。2.1.97 提到压缩的 “prompt-too-long retries”。
  • 文档写了压缩的兜底办法：一轮完整对话都摘要不了时，原样保留最新一条用户提示，摘要它之前的全部内容。这和截掉头部是两种不同的兜底，文档没有写截头。
  • 有损属实（实测）：截头重试后，摘要只剩标题。
  • StopFailure 的触发与文档不完全一致。文档说它在回合因 API 错误结束时 “Runs instead of Stop”；实测中它在摘要请求被拒时就触发了，回合随后正常结束，Stop 也运行了。只在这个版本上测过 2 次。

中断也是错误恢复的一部分

原文 6.7

原文说，很多人把 abort 归为交互体验，不放进错误恢复讨论。从运行时角度看，中断是必须正确回收的失败状态。原文说 Claude Code 在两层都处理了：

  • query 层。 流式输出被打断时，先消费 StreamingToolExecutor.getRemainingResults()，为悬空的 tool_use 生成 synthetic tool_result。
  • compact 层。 compact.ts 把 compact 的 abort controller 传给 forked agent，并处理 APIUserAbortError，防止“被 Esc 的 compact”误算成一次成功摘要。

原文说，中断不只是“用户不想看了”，而是需要正确收尾的状态转移。错误恢复只管异常、不管中断，会留下语义半残的执行轨迹：短期无人查，长期都是祸根。

事实核对
  • StreamingToolExecutor.getRemainingResults()、abort controller、APIUserAbortError 等名字无法核对：源码不公开。
  • 补齐 tool_result 属实（观察，见第 3 章）。本机 6 次中断里，被打断的调用都拿到 is_error 的 tool_result，随后有一条 “[Request interrupted by user for tool use]”。
  • 中断的压缩不算成功属实（文档）。errors 文档写到：压缩时按了停止，之后出现 prompt too long 报错，“your conversation is unchanged and still large enough to need compacting”。CHANGELOG 2.1.302 和 2.1.304 都修过“压缩中途停止后报 Prompt is too long”的问题。
  • 压缩由单独的请求完成（观察）：摘要请求标记为 compact，沿用主会话的 system prompt 和工具定义，并要求 “Respond with TEXT ONLY”。是否叫 forked agent，无法核对。
  • 本次没有在 2.1.312 上重做中断实测。

原文 6.8

  • 刚才试图做什么，为什么没做成。
  • 用了什么恢复路径。
