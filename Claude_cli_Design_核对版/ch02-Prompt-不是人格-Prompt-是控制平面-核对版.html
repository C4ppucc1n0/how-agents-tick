A

核心观点：人设和控制平面不在同一层

原文 2.1

一说起 system prompt，很多人想到的是人设：你是谁、你擅长什么、最好再有一点稳定的人格。这对聊天系统够用。对要读文件、调工具、动 shell、跨轮执行的代理系统，就不够了。

人设 控制平面
解决的问题 它像什么 它能做什么、什么时候做、做错了怎么办、谁来兜底
形态 一篇人物小传 一组分层拼装的行为区块
更接近 台词 运行时协议

原文说，Claude Code 的 system prompt 属于后者。

Prompt 控制平面
  • 分层prompt 是一组 section，而不是一段字符串（B）
  • 优先级多个来源按固定顺序装配（C）
  • 连接记忆CLAUDE.md 和记忆规则也进入上下文（D）
  • 考虑缓存区分稳定部分和会变的部分（E）
  • 可覆盖但有结构用户可以改内容，装配结构不变（F）

（这五个方面对应原文 2.7 列出的结构条件，分组是本页归纳。）

本节是原文的观点，不涉及需要核对的事实。

B

prompt 从一开始就是分层的

原文 2.2

原文说，getSystemPrompt() 返回一个由多个 section 组成的数组，而不是一段完整字符串。prompt 一旦变成多个块，系统就承认了它内部有一组职责不同的约束。原文列出三类 section：

system prompt 的 section（按原文）
  • 身份与总任务
    • 交互式代理，用工具帮用户完成软件工程任务
    • 夹带安全约束，例如不要乱猜 URL
  • 系统级规则
    • 用户能看见哪些文本
    • 工具调用可能触发权限审批
    • 用户拒绝后不能机械重试
    • 工具结果和用户消息里可能混入 system-reminder
    • 上下文会被自动压缩
  • 做任务时的工程性指令
    • 不要随意增加需求
    • 不要越权优化
    • 不要为了显得完整而隐瞒验证失败
    • 不要在没必要时制造抽象

原文说，系统级规则不关心模型“像不像聪明助手”，而关心它是不是一个守规矩的执行体。这就是控制平面的语气：核心任务是定义边界。工程性指令看起来像写作风格要求，其实和工程约束绑得很紧。一个会“顺手优化一切”的模型，从产品角度看也许很热情，从工程角度看却相当危险。

D

prompt 还连接着记忆系统

原文 2.4

原文说，在 Claude Code 里，prompt 是整个上下文治理的入口，而不只是“写给模型看的一段话”。它举了两个函数：

  • getClaudeMds()：把项目指令、个人项目指令、团队共享的 team memory 和跨会话的 auto memory 整理成统一格式。整理后的内容拼进 prompt 相关上下文。每段内容都写明来源。
  • buildMemoryLines()：把“怎样保存记忆”也写进 prompt。它告诉模型五件事：memory 是文件化的持久系统；MEMORY.md 是索引，不是正文；frontmatter 怎么写；哪些信息不该保存；plan 和 task 不该被误用成 memory。

这些说明前面有一句开场：“These instructions OVERRIDE any default behavior and you MUST follow them exactly as written.”（观察）。文档说，所有找到的 CLAUDE.md 按从宽到窄的顺序拼接，而不是互相覆盖。

记忆规则：两版 prompt 对照

原文说 prompt 告诉模型的 完整版 短版
memory 是文件化的持久系统 ✓“persistent, file-based memory system” ✓“persistent file-based memory”
MEMORY.md 是索引，不是正文 ✓“MEMORY.md is an index, not a memory” ✓写明它是索引，不要把记忆内容写进去
frontmatter 怎么写 ✓给了模板 ✓给了模板
哪些信息不该保存 ✓“## What NOT to save in memory” 一节 ✓一句话：仓库里已有的、只和本次对话有关的不存
plan 和 task 不该当成 memory ✓“## Memory and other forms of persistence” 一节 ✗没有

原文由此说：这一步把 prompt 的职责从“约束当前行为”扩展到“约束未来知识怎样沉淀”。Claude Code 不只用 prompt 规定这一轮怎么说话，还用它规定长期记忆怎样形成。走到这一步，prompt 就不再是语气问题，而是制度问题。

事实核对
  • getClaudeMds()、buildMemoryLines() 和原文给的文件位置（src/utils/claudemd.ts、src/memdir/memdir.ts）无法核对：源码不公开。
  • “统一格式，写明来源”行为属实（实测、观察）。项目指令、个人项目指令、auto memory 各有一句来源标签，见上图。
  • 补充位置：这些内容不进 system 字段，而是放在第一条用户消息里（实测）。文档也说 system reminder “in the conversation, not in the system prompt”。
  • team memory 本次没有观察到。CHANGELOG 提到过 team memory stores（CLAUDE_MEMORY_STORES），只能说明这个机制存在（旁证）。
  • 记忆规则：完整版五条都有；默认短版缺“plan 和 task 不该当成 memory”那一条（实测）。
E

控制平面还要考虑缓存与计算成本

原文 2.5

多数人理解 prompt 时很少想到性能。但 prompt 同时也是计算成本：越复杂、变化越频繁，缓存命中就越差，系统就越贵、越慢。原文说，Claude Code 把 prompt section 分成两类：

section 类型 缓存 说明
systemPromptSection 可缓存 resolveSystemPromptSections() 优先从缓存取，只在必要时重算
DANGEROUS_uncachedSystemPromptSection 会打破缓存 名字里的 DANGEROUS 提醒使用者它的代价

原文还说，执行 /clear 或 /compact 后，clearSystemPromptSections() 会清空这些缓存状态。getSystemPrompt() 用一条 boundary 把静态部分和动态部分显式分开。

原文说，这说明设计时已经承认：有些内容相对稳定，有些内容逐轮变化，两者不能混在一起消耗缓存。一个系统一旦开始关心“哪部分 prompt 会让缓存失效”，就不再把 prompt 当作文案创作：

事实核对
  • 两类 section 的名字和 resolveSystemPromptSections()、clearSystemPromptSections()，以及原文给的文件位置（src/constants/systemPromptSections.ts），无法核对：源码不公开。
  • 行为层与原文一致（见上表）。注意文档说的 API 缓存只按前缀匹配，“There is no per-file or per-segment caching”。原文说的按段缓存，指 Claude Code 自己保存算好的段落。这一层从外部看不到。
  • 实测三次运行，工具定义和身份句相同、主 prompt 不同。后两次都从缓存读了 12,542 个 token，主 prompt 及之后的内容重新写入。这与“前面不变的部分能复用缓存”一致。
  • 自定义 prompt 的边界：实测经本机网关时，边界那一行被删掉，但两部分仍在一个块里。文档写明经 LLM 网关时 “sends the whole prompt as one block”，两者一致。
F

用户可以覆盖 prompt，但不能跳过结构

原文 2.6

Claude Code 没有把用户锁死在默认 prompt 上，CLI 明确支持覆盖和追加。原文列了四个选项：--system-prompt、--system-prompt-file、--append-system-prompt、--append-system-prompt-file。

关键在于：无论用户怎样覆盖和追加，最终都由同一个 buildEffectiveSystemPrompt() 装配。系统允许自定义，但不放弃秩序；用户可以改内容，系统保留结构。

没有结构的可定制，最后往往退化成另一种随意。今天加一段，明天减一段，后天某个 agent 又替换掉基线约束，系统行为就越来越像临时口头通知。原文说，Claude Code 的选择是：允许修改，但修改必须发生在既定的优先级和分层机制里。

G

prompt 更像宪法，而不是台词

原文 2.7

台词是给角色在场上说的；宪法规定权力边界、责任关系，以及例外情况怎样处理。原文说，Claude Code 的 prompt 更接近宪法，因为它满足五个结构条件：

结构条件 而不是 核对 详见
分层 一块写到底 ✓行为属实，命名无法核对 B
有优先级 谁后写谁说了算 ✓行为属实；agent 与 custom 的先后无法核对 C
与 memory、CLAUDE.md、agent instructions、MCP instructions 一起组成控制平面 孤立的一段文字 ✓CLAUDE.md 和记忆实测属实；MCP 说明本次没配置 D
有缓存和动态 section 机制 随手拼一段文本 ✓行为属实，命名无法核对 E
和运行时紧密耦合 游离于系统之外的装饰物 ✓观点，依据见各节 B–F

原文说，单独“写一个好 prompt”价值有限。更重要的问题是：prompt 在系统里处于什么位置，和哪些模块配合，是否参与权限、状态、上下文和长期记忆的治理。不回答这些问题，所谓好 prompt 往往只在某个顺利的场景里暂时成立。

事实核对
  • MCP 服务器说明：文档说它会占用上下文；本次没配置 MCP 服务器，它放在哪里没有观察到。
  • 其余四条的依据见 B–F 的“事实核对”。
H

从源码提炼的第二个原则

原文 2.8
第二个原则

Prompt 的价值，在于它是否被纳入一套清楚的控制结构。

原文说，源码在五个地方共同证明了这一点。源码不公开，下表把原文的证据换成核对后的依据：

原文的源码依据 说明什么 核对后的依据 详见
constants/prompts.ts 把 prompt 写成分段的控制结构，而不是一段统一宣言 主 prompt 按标题分节，记忆一节能单独移走（实测）；默认短版比完整版简略得多（文档、实测） B
utils/systemPrompt.ts 明确规定 prompt 来源的优先级 替换、代理、追加三种来源的组合结果固定（文档、实测） C
utils/claudemd.ts 把项目级内容和长期记忆纳入上下文装配 CLAUDE.md、CLAUDE.local.md、MEMORY.md 带来源标签进第一条用户消息（实测、观察） D
memdir/memdir.ts 用 prompt 规定长期记忆的保存规则 两版 prompt 都有记忆规则；短版缺 plan 和 task 那一条（实测） D
constants/systemPromptSections.ts 把 prompt 变成可缓存、可失效、可按段重算的运行时对象 首次构建后复用，压缩或清空后重建；动态段能移出 system 字段（文档、实测） E

原文提炼的工程原则：成熟代理系统里，prompt 不是“让模型入戏的开场白”。它更像一套运行中的制度文本。制度文本当然可以写得清楚，但最重要的始终是约束力。核对后，五处证据都能换成文档或实测依据，论点成立。需要补充两点：

  • 约束的密度随 prompt 版本变化，默认短版比完整版少很多条。
  • 项目说明和记忆不在 system 字段里，而在对话消息里。“prompt”在这里应理解为整个上下文，而不只是 system 字段。
