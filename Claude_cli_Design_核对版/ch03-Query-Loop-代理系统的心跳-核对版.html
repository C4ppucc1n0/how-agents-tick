一句话结论：原文认为，代理系统的核心能力是维持可恢复的执行循环，在 Claude Code 里就是 queryLoop()。

核对后，论点成立。流式调用、提前执行工具、中断补齐 tool_result 都有观察或实测依据。截断后自动续写、Stop hook 阻塞后再来一轮，也在 v2.1.312 上实测到了。prompt 太长时先压缩、救不回来才报错，API 错误先重试；这两点用第 6 章的故障注入实测到了。函数名、状态字段和治理步骤的顺序无法核对。

A

一个代理系统是否成熟，先看它有没有循环

原文 3.1

把会写代码的模型当成加强版问答接口，是最常见的错误。系统一旦开始调用工具、跨轮执行、处理中断、保存状态、压缩上下文，“一问一答”就失效了。原文说，Claude Code 从结构上承认：代理依赖一段持续的、有状态的执行过程。

原文的依据是源码：query() 只是一层壳，核心是 queryLoop()。它维护一套跨迭代的状态，先做调用前的治理，再进入流式阶段。模型返回后，它再决定执行工具、恢复、压缩、继续下一轮，还是终止。

原文用 lifecycle（生命周期）概括这一点。一个系统能否称为 agent，不在于它会不会说，而在于几轮之后它还知不知道自己在做什么。

原文的图：一次迭代的结构

原文在这里放了一张图，标题是 “Query Loop Core - One Iteration Of The While Loop”。图的意思是：循环状态跨迭代保留，喂给每次迭代。一次迭代依次是调用前治理、模型流、工具执行、应用结果、决定下一步。下图按事实重画。+ 表示按事实补上，− 表示原图有、但与事实不符。切换 Before 和 After，可以分别看原图结构和修正后的结构。

事实核对
  • query()、queryLoop() 和原图的节点名无法核对：源码不公开，文档里也没有这些名字。
  • 循环本身有依据。文档说 agentic loop 分 gather context、take action、verify results 三个阶段，用户 “can interrupt at any point”。实测：一条提示产生了 3 次 API 请求，依次是调用工具、回答、被 Stop hook 阻塞后补答。
  • 原图从“不需要继续”直接画到“结束本轮”。实测中，回答结束后先运行 Stop hook，hook 阻塞时会再来一轮。重画时补上了这一段（附录第 3、21 条）。
B

状态属于主业务

原文 3.2

很多系统把状态当成包袱，认为无状态更优雅。但代理系统一进入真实工作流，状态就会自然出现。忽视状态并不能消除它，只会让它以更难管理的方式回来。

原文说，Claude Code 把 query loop 的可变状态明确定义为 9 项（下面的分类是本页归纳）：

State
对话与工具messages、toolUseContext
压缩与恢复autoCompactTracking、maxOutputTokensRecoveryCount、hasAttemptedReactiveCompact
轮次与流转turnCount、transition、stopHookActive、pendingToolUseSummary

每次 query loop 启动时，这些状态被整体装配成一个 State 对象，之后在每个 continue 分支里整体更新。恢复、压缩、预算、hook、轮次计数没有散落在局部变量里，因为它们共同决定“本轮结束后，下一轮如何继续”。脚本只关心这一步有没有跑完；代理系统还要关心，这一步失败后，下一步能不能接住前面留下的状态。

不变式 含义 核对 依据
状态单调 turnCount 只增不减 无法核对 源码不公开
账本对齐 每个发出的 tool_use 都有对应的 tool_result ✓行为属实 观察：本机 104 个会话记录共 8490 次工具调用，只有 2 次没有结果。这 2 次都是文件里最后一次调用

事实核对
  • 9 个字段名和“整体装配、整体更新”无法核对：源码不公开。
  • 有一项状态能从外部看到。文档说，Stop hook 的输入里有 stop_hook_active，Claude Code 因 Stop hook 而继续时它为 true。实测中，第一次 Stop 调用为 false，hook 阻塞后的第二次为 true。这说明“stop hook 是否已经生效”确实跨迭代保存。
  • 防自回环：原文说试过一次就不再压缩。现状是，压缩后的请求仍太长时，Claude Code 会再压一次，保留更少的近期对话（CHANGELOG 2.1.284）。自动压缩连续几次后上下文立刻又满，Claude Code 会停止并报 thrashing 错误（文档）。防止无限压缩这个目的成立，但“只压一次”与现状不符。

原文认为，这串顺序本身就是一种架构声明：Claude Code 把上下文治理放在模型推理之前。它不把“从混乱中整理秩序”的责任交给模型，而是由运行时先整理好，再把更干净的输入交给模型。很多系统的做法相反：先把大量上下文塞进去，再指望模型自己判断什么重要。这看似省事，实际上是把运行时该承担的责任转嫁给了概率分布。

D

调用模型只是循环的一段

原文 3.4

治理完成后才进入模型调用。原文指出一个细节：系统用 for await 流式消费模型输出，而不是同步拿回一个完整结果。所以模型输出在 Claude Code 里是一串事件，可能是 assistant 文本、tool_use block、usage 更新、stop reason 或 API 错误。系统把 assistant message 存起来，提取 tool_use，判断是否需要 follow-up，还可能边流边把工具送给 StreamingToolExecutor。

（示意：按原文文字画，参与者名字取自原文。）

一旦把模型输出当成事件流，架构就不再是“请求-响应”，而是“驱动-调度-反馈”。流式输出的意义不只是早点看到几个字，而是让运行时在模型还没结束时，就开始安排下一步执行。所以原文说，心跳是整个循环，而不是模型调用本身。

实测：回复还没结束，工具已经跑完

实测让模型在同一条回复里先调用 Glob，再调用 Write 写一段约 600 字的故事。Write 的参数很长，模型要生成好几秒。下面的时间以发出第 1 次请求为 0（实测，v2.1.312）：

  1. 0 s发出第 1 次请求请求带 stream: true
  2. +2.0 sGlob 开始执行PreToolUse hook 触发
  3. +2.5 sGlob 执行完PostToolUse hook 触发
  4. +6.7 s第 1 次回复结束stop_reason 为 tool_use，共 847 个输出 token
  5. +7.0 sWrite 开始执行回复结束后才开始
  6. +7.3 s发出第 2 次请求带上两个 tool_result
事实核对
  • StreamingToolExecutor 这个名字无法核对：源码不公开。
  • “边流边执行工具”行为属实：Glob 在回复结束前约 4.6 秒就执行完了。会话记录印证了这一点：Glob 的 tool_result 写于 06:33:15.7，同一条回复里的 Write 块到 06:33:19.9 才结束。
  • 流式调用属实：抓到的请求全部带 stream: true，响应带 stop_reason 和 usage。
  • 局限：只做了一次，只看到只读工具提前执行。Write 为什么等到回复结束才执行，从外部分不清。

原文 3.5

一个循环不仅要能持续运行，还要能在必要时停下来。停不下来，系统就只剩惯性。原文说，Claude Code 会优先处理 streaming abort：

（示意：按原文文字画。）

背后的原则是：系统一旦对外承诺了一段执行，中断时就要把账补平。不能因为用户打断了，就假装前面的 tool_use 从未发生。外部系统、UI 和 transcript 都需要一条一致的因果链，哪怕结果是“中断了”，也要中断得完整。解释不了的执行轨迹，迟早会变成运维问题或审计问题。

事实核对
  • 两个分支和 yieldMissingToolResultBlocks 无法核对：源码不公开。
  • “中断时补齐 tool_result”行为属实（观察）。本机会话记录里有 6 次中断，版本是 2.1.284 到 2.1.296。每次被打断的调用都拿到一条 is_error 的 tool_result，内容是 “The user doesn't want to proceed with this tool use…”，随后是一条 “[Request interrupted by user for tool use]”。
  • 文档：按 Esc 后 “The running tool call is canceled”；用户中断时 Stop hook 不运行。
  • 局限：中断样本来自旧版本，没有在 2.1.312 上重做。
F

心跳还必须能恢复

原文 3.6

中断是外部打进来的意外，恢复是系统内部预留的余量。没有恢复能力的循环，等于把幸运当成了设计。原文说，Claude Code 的恢复层层递进，不是简单重试。最典型的是下面两种。

prompt 太长（prompt-too-long）

原文说，系统先判断最后一条 assistant message 是不是被暂扣（withheld）的 prompt-too-long 错误。如果是，先让 context collapse 把积压提交出去；还不够，再做 reactive compact。恢复手段按成本和破坏性从低到高逐层尝试。下图按事实补了一段，+ 表示按事实补上：

输出超长（max-output-tokens）

原文说，系统先尝试提高 token 上限；还不行，再追加一条 meta 消息，让模型从截断处继续往下做，而不是先道歉、先总结。

（示意：按原文文字画。）

原文评价：Claude Code 把恢复看成运行时主路径的一部分，而不是模型失败后的礼貌动作。恢复的意义是给系统一个继续工作的机会。

事实核对
  • prompt 太长：文档说，遇到 Prompt is too long 时会自动压缩，通常概括最早的对话、保留最新的；压缩失败时报 “Prompt is too long · automatic compaction failed”。CHANGELOG 2.1.284 补上了第 3 步。withheld 和 context collapse 无法核对。
  • prompt 太长的实测（见第 6 章故障注入）：注入一次时，约 0.2 秒后自动压缩并重试，用户看不到这个错误；一直注入时，压缩两次后报 “Prompt is too long”。第 3 步属实。
  • 文档还写了一种更轻的恢复：输入加 max_tokens 超过上下文上限时，先减小 max_tokens 重试，减不下去才压缩。
  • 输出超长：续写行为属实（实测）。把上限设成 400 后，回复两次被截断，Claude Code 两次追加同一条用户消息：“Output token limit hit. Resume directly — no apology, no recap of what you were doing. Pick up mid-thought if that is where the cut happened. Break remaining work into smaller pieces.” 第三次回复正常结束。
  • “提高上限”这一步本次没观察到。用环境变量设上限时，三次请求都是 400；默认配置下请求的 max_tokens 已是 128000（claude-haiku-5-5）。文档没写自动续写，只写了最终报错和手动回复 continue。
G

停止条件不能只有一个

原文 3.7

问答系统有回答就结束。代理系统不行：“当前轮结束”不等于“任务完成”，更不等于“系统成功”。原文说，queryLoop() 至少区分了下面这些情况。表里最后一列是核对结果：

事件 前置状态 触发 下一步 核对
流正常结束，有 tool_use 有未完成的 tool_use stop reason follow-up，进入工具执行 ✓实测：stop_reason 为 tool_use，执行工具后发下一次请求
流正常结束，无 tool_use 没有待处理的工具 stop reason 进入 stop hooks ✓实测：end_turn 后运行 Stop hook
用户中断 任意 abort signal 消费剩余结果，生成 synthetic tool_result ✓观察：被打断的调用都有 is_error 的 tool_result
prompt 太长 还没试过 compact 可恢复错误 走 collapse 或 reactive compact !实测：自动压缩后重试，一回合最多两次；collapse 无法核对
输出超长 上限未到最大 stop reason 提高上限后重跑 !本次未观察到
输出超长 上限已到最大 stop reason 追加 meta 消息，续写 ✓实测：两次续写后正常结束

防止死循环

原文说，stop hooks 这段代码专门防了一种死循环：compact 后仍然太长，再被 hook 阻塞，再继续 compact。

（示意：按原文文字画。）

许多系统的想法是“失败了就重试”。Claude Code 则承认重试本身也要被管理：为什么重试、已经试过什么、哪些保护状态不能重置、哪些情况会无限循环。这些判断区分了“会继续试”的系统和“知道什么时候不该再试”的系统。

事实核对
  • API 错误：文档说，Claude Code 对瞬时失败（服务器错误、过载、超时、临时 429、断线）“retries … up to 10 times with exponential backoff before showing you an error”。回复中途失败时，它保留已完成的部分，执行已完成的工具调用，然后继续这一轮。API 错误时触发 StopFailure hook，不运行 Stop hook。实测（第 6 章）：让每次请求都返回 529，Claude Code 共发了 11 次请求，间隔从约 0.6 秒逐次翻倍，最后报错并触发 StopFailure。重试在哪一层做无法核对，所以“queryLoop 本身不重试”可能仍然成立；但从行为上看，Claude Code 不是“直接返回，不重试”。
  • Stop hook 阻塞后再来一轮：属实（实测）。hook 返回 block 后，下一次请求多了一条 “Stop hook feedback: …” 用户消息。
  • 防死循环属实（实测，见第 6 章）。先让 Stop hook 阻塞一次，再让每次请求都返回 prompt too long：Claude Code 压缩两次后报错，跑 StopFailure，Stop hook 没有再运行，没有出现循环。文档还写了另外两种防循环保护：Stop hook 连续续跑 8 次后，Claude Code 不再接受阻塞；自动压缩连续无效时，Claude Code 停止并报错。原文“重试也要被管理”的论点有这些依据支撑。
H

QueryEngine：循环属于会话生命周期

原文 3.8

原文说，QueryEngine 的源码注释直接写明了它的职责：

QueryEngine owns the query lifecycle and session state for a conversation.

也就是说，它管理的是一整个对话的生命周期，而不是某一次调用。一个 QueryEngine 对应一个对话；每次调用 submitMessage()，都是在同一个对话里开始新的一轮，状态持续保存。QueryEngine 把准备好的 messages、systemPrompt、userContext、systemContext、toolUseContext 一起交给 query()，再把 assistant、user、compact boundary 等消息写回 transcript。

原文由此认为，query loop 是会话系统真正的执行中心，UI、SDK 和 session persistence 都围着它转。要理解 Claude Code，不能只看它有哪些工具、prompt 写了什么，最终要看这个循环怎样把各种约束落实成连续的行为。

代理系统的核心能力，是维持可恢复的执行循环。
