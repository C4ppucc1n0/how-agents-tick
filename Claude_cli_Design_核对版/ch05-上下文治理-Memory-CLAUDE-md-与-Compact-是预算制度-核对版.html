A

核心观点：上下文是预算，不是仓库

原文 5.1

“信息越多，系统越聪明”是一个危险的神话。代理系统不是图书馆，上下文也不是“存进去就算拥有”的仓库。原文说，上下文首先是一笔昂贵、易膨胀、会自我污染的预算。

Claude Code 在这件事上很不浪漫。该加载什么、该截断什么、什么要长期保留、什么只能短期摘要，全是运行时要严肃治理的事。本章讨论的是：Claude Code 怎样防止自己被记住的东西拖死。“记住更多”和“治理记忆”看起来相近，在工程上是两种制度。

上下文治理的四层（本页归纳）
  • 长期规则CLAUDE.md 体系，分层加载（B）
  • 长期记忆MEMORY.md 当索引，正文放主题文件（C）
  • 会话连续性session memory 模板（D）
  • 窗口预算自动压缩，压缩后重建工作环境（E、F、G）

本节是原文的观点，不涉及需要核对的事实。

B

CLAUDE.md 体系：长期指令不和临场对话混在一起

原文 5.2

原文说，claudemd.ts 开头就把记忆层次说清楚了。指令来源分四层：

指令来源
  • managed memory例如 /etc/claude-code/CLAUDE.md
  • user memory例如 ~/.claude/CLAUDE.md
  • project memory项目根目录的 CLAUDE.md、.claude/CLAUDE.md、.claude/rules/*.md
  • local memory例如 CLAUDE.local.md

原文说，这些文件按优先级和目录距离加载。离当前工作目录越近的项目规则，优先级越高；越私有、越本地的规则越晚加载，因而越靠近模型的注意力前沿。

这说明 Claude Code 拒绝把“长期协作规则”和“本轮临时对话”混在一起。团队规范、个人偏好、仓库约束，寿命远长于某一轮用户消息。全塞进聊天记录，系统就会在两个极端之间摇摆：要么每轮重复注入，浪费上下文；要么靠模型自己回忆，迟早失手。claudemd.ts 的答案，是把稳定规则做成可发现、可分层、可组合的持久指令系统。

原文还提到一个细节：它支持 @include，并且只允许一批明确列出的文本扩展名。这说明工程师在提防另一种事故：有人把二进制文件、巨型文档，甚至不该进 prompt 的东西糊里糊涂带进来。原文说，这是一种克制：系统先问什么值得进入记忆，什么一进入就是污染。

事实核对
  • 原文给的文件位置（src/utils/claudemd.ts）无法核对：源码不公开。
  • 四层来源属实（文档）。文档列出的路径与原文一致；Windows 上 managed 的位置是 C:\Program Files\ClaudeCode\CLAUDE.md。
  • 加载顺序属实（文档、实测）。文档说文件按从文件系统根到工作目录的顺序排列，同一目录里 CLAUDE.local.md 排在 CLAUDE.md 之后。实测中，上层目录的 CLAUDE.md、项目的 CLAUDE.md、CLAUDE.local.md 依次出现。
  • “优先级越高”与文档不符。文档说所有文件 “are concatenated into context rather than overriding each other”；两条说明冲突时，“Claude may pick one arbitrarily”。靠后的说明更靠近对话，但不保证胜出。

C

MEMORY.md 是索引，不是日记本

原文 5.3

如果 CLAUDE.md 管规则，memdir 管的就是另一类更细的长期记忆。原文说，memdir.ts 把入口文件 ENTRYPOINT_NAME 定为 MEMORY.md，但不鼓励往里堆内容，而是把它定义为索引。buildMemoryLines() 告诉模型，保存 memory 分两步：

  1. 把具体内容写进一个独立文件。
  2. 在 MEMORY.md 里加一行指向它。

为什么这么麻烦？原文说，入口文件会被频繁加载，一旦变胖，整套上下文就会被它慢慢拖垮。所以 memdir.ts 设了 MAX_ENTRYPOINT_LINES = 200 和 MAX_ENTRYPOINT_BYTES = 25_000。超过时，truncateEntrypointContent() 直接截断，并在末尾追加警告：只加载了一部分，请把细节移到主题文件。

原文说，这是把“入口必须短”做成硬约束。入口文件一旦既当目录又当正文，最后既不是目录，也不是正文。由此得出的原则是：长期记忆必须分成“入口”和“正文”。入口负责低成本寻址，正文负责高密度承载。

实测：MEMORY.md 超限时怎样截断

实测把 auto memory 目录指向临时目录，放进两份超限的 MEMORY.md：

MEMORY.md 载入的部分 末尾追加的警告（原话摘录）
260 行，约 9.6KB 前 200 行 “MEMORY.md is 260 lines (limit: 200). Only part of it was loaded: 60 of 260 lines were cut off”
150 行，约 37.5KB 前 98 行 “MEMORY.md is 37.5KB (limit: 24.4KB) — index entries are too long”

两条警告都以 “Keep index entries to one line under ~200 chars; move detail into topic files.” 结尾。

事实核对
  • 常量名、truncateEntrypointContent() 和原文给的文件位置（src/memdir/memdir.ts）无法核对：源码不公开。
  • 两步保存属实（实测）。完整版和短版 system prompt 都要求先写独立文件，再在 MEMORY.md 加一行指针。
  • 200 行和 25,000 字节两个上限属实（文档、实测）。文档写作 “first 200 lines or 25KB”；实测警告写 “limit: 24.4KB”，正好是 25,000 字节。
  • 截断后追加警告属实（实测），警告原话见上表。
  • 文档还写到一层约束。Claude 写 MEMORY.md 后，Claude Code 会量一下大小：接近上限时提醒缩短，超过上限时返回错误，要求重写索引。
D

Session memory：短期连续性也不能靠聊天记录硬扛

原文 5.4

只有长期 memory 还不够。代理系统真正难受的地方，常常是“这轮之前我们做到哪一步了”，这是会话内部的连续性问题。原文说，SessionMemory/prompts.ts 专门为此建了一套模板，默认有九个栏目：

session memory 模板（按原文）
  • 进度Current State、Worklog、Key results
  • 任务与代码Task specification、Files and Functions、Workflow
  • 经验Errors & Corrections、Learnings、Codebase and System Documentation

（分组是本页归纳，栏目名取自原文。）

原文说，更新 notes 的 prompt 有五条要求：

  • 只能用 Edit 工具更新 notes 文件。
  • 不要提记笔记这件事本身。
  • 不要改模板结构。
  • Current State 必须始终反映最近的工作。
  • 每节都要信息密集，但要控制预算。

所以 session memory 不是“另存一份聊天记录”，而是把当前会话提炼成一份能继续工作的操作说明。原文还说，MAX_SECTION_LENGTH = 2000，MAX_TOTAL_SESSION_MEMORY_TOKENS = 12000。超过预算时，系统要求 aggressively condense，优先保住 Current State 和 Errors & Corrections。原文的判断是：上下文预算是工作内存，工作内存的第一职责是可操作。

事实核对
  • 模板、五条要求、两个预算常量和原文给的文件位置（src/services/SessionMemory/prompts.ts），都无法核对。源码不公开，文档没有写 session memory，本机也没有找到 session memory 文件。
  • CHANGELOG 2.1.50 写到 CLAUDE_CODE_SIMPLE 会去掉 “skills, session memory, custom agents”，只能说明这个机制存在（旁证）。没观察到不等于没有，功能可能按账号或实验开关。
  • 本机能看到的是另一种机制：压缩摘要（观察）。压缩请求要求摘要按九节写，包括 Errors and fixes、Pending Tasks、Current Work、Optional Next Step。它同样服务“继续工作”，但不是原文说的 session memory。
E

自动 compact：上下文治理首先是预算治理

原文 5.5

到这里，长期规则、持久 memory、session memory 都有了，但上下文还是会膨胀。原文说，autoCompact.ts 承认一个现实：对话够长，总会逼近窗口边缘。

  • getEffectiveContextWindowSize() 先从模型窗口里减去一笔给摘要输出的预算，MAX_OUTPUT_TOKENS_FOR_SUMMARY 预留 20,000 tokens。系统先假定 compact 本身要花钱，不会等窗口只剩一口气才想起求生。
  • getAutoCompactThreshold() 再从有效窗口里扣掉 AUTOCOMPACT_BUFFER_TOKENS = 13_000。警告阈值、错误阈值、手动 compact 也各自留有缓冲。

原文说，道理很朴素：上下文治理要提前为失败和恢复留出余地。不留余地的系统，平时看着节俭，出事时才暴露真相：风险账单留给了下一轮。

原文还说，AutoCompactTrackingState 不只记是否压缩过，还记 turnCounter、turnId 和 consecutiveFailures。autocompact 是一段会被追踪、会失败、会被限流的运行时行为。源码注释写得很直白：全球每天曾浪费大量 API 调用在连续失败的 autocompact 上，所以失败 3 次就触发熔断。原文说，你可以失败，但不能无限次、无记忆地失败。

事实核对
  • 函数名、常量名、AutoCompactTrackingState 的字段、注释原话和原文给的文件位置（src/services/compact/autoCompact.ts），无法核对：源码不公开。
  • 预留空间：文档说 1M 窗口的模型约在 967K 时压缩，正好是 1M 减去 20K 和 13K。本机观察到的触发点也在窗口减 33K 附近（上表）。两笔预算的合计有依据，各自多少无法拆分。
  • 实测的压缩请求 max_tokens 是 128,000，不是 20,000。20K 如果存在，只用于计算阈值，不是摘要输出的上限。
  • 熔断属实（旁证）：CHANGELOG 2.1.76 写到，自动压缩连续失败后会无限重试的问题已修复，“a circuit breaker now stops after 3 attempts”。
  • 文档另写了一种保护：压缩成功、但上下文立刻又满，连续几次后报 “Autocompact is thrashing”，停止重试 “to avoid wasting API calls”。

原文 5.6

很多人以为 compact 就是“把前面聊天摘要一下”。原文说，compactConversation() 先把原有上下文拆开、摘要，再注入必要附件，重新搭出一个还能工作的环境。下表按原文的顺序列出每一步，并给出核对结果：

阶段 原文说的动作 核对
压缩前 把图片、文档替换成 [image]、[document] 等标记 ✓旁证：2.1.47 起压缩前 “stripping document blocks alongside images”
压缩前 剥掉之后会重新注入的附件 无法核对：实测的压缩请求里，第一条消息的 CLAUDE.md 内容仍在
摘要失败 压缩请求本身 prompt too long 时，截掉开头重试 ✓旁证：摘要请求过长时会重试；另观察到格式不对时的重试
压缩后 清空旧的文件读取状态，重新生成最近文件的附件 ✓文档、观察：最多重读五个最近改过的文件
压缩后 补回 plan 附件 ✓文档、观察
压缩后 补回 plan mode 附件 无法核对：本机压缩后没有观察到
压缩后 补回已调用技能的附件 ✓文档、观察
压缩后 补回 deferred tools、agent listing、MCP instructions 的增量附件 !前两种观察到；MCP 没有条件观察

原文说，这些动作合起来，目标是把“继续干活所需的运行时环境”重新铺平，摘要只是中间产物。所以 compact 更像一次受控重启，而不是一次聊天总结。很多系统只做前半截，压缩后虽然“还记得个大意”，却丢了工具状态、计划状态、附件状态，还得再花几轮找回自己。

事实核对

  • 文档的 “What survives compaction” 表与原文的清单基本一致：项目根 CLAUDE.md、auto memory 从磁盘重新注入；技能说明重建；plan 从磁盘重新注入；最多重读五个最近改过的文件，超过 5,000 tokens 的只给路径；SessionStart hook 用 compact 作为 source 运行。文档另有 PostCompact hook。

G

上下文治理的关键是保留工作语义

原文 5.7

原文说，compact.ts 的后半段有一个贯穿始终的倾向：保住工作语义。

  • 恢复最近访问文件的附件，因为这些文件往往是当前工作面的局部现实。
  • 恢复 plan mode，否则模型压缩完可能忘了自己还在 plan 的纪律里。
  • 保留已调用技能的内容，但给每个技能设 token 上限，免得技能在压缩后反客为主。

源码里有一句话：per-skill truncation beats dropping。即使要裁，也优先保住开头那段最关键的指令，而不是整个扔掉。原文说，这就是治理，不是纯粹节流：节流是砍，治理是知道该砍哪里、该保什么。

由此得出一条经验：上下文系统应该优先保留能维持行动语义的东西，而不是看起来信息量最大的东西。

应该保留 不必再占位置
文件细节、当前计划、错误修正、技能约束 冗长历史对话、重复附件、运行时随时能重新拿到的内容

原文提炼的工程原则：

  • 长期规则、长期记忆、会话连续性应分层，不混写。

  • session summary 服务“继续工作”，不是“回忆完整”。
