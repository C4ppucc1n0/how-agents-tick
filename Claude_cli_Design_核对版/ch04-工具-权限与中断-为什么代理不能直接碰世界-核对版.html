需要修正四点：

  • 权限判定的顺序与原图不同。PreToolUse hook 最先运行；规则层不只能拒绝，ask 规则在任何模式下都要人批准，allow 规则也能直接放行。
  • 并行工具里一个失败，不再取消其他工具（CHANGELOG 2.1.161 起；实测）。原文正文说会取消，原文矩阵说其他工具照常，两处本身不一致。
  • 并行工具的结果按完成先后进入下一次请求，不按调用顺序（实测）。
  • 实测 200 段的复合命令照常执行，没有观察到 subcommand 上限。文档写的兜底是请求批准，不是直接拒绝。

A

核心观点：工具不是意见，是动作

原文 4.1

只输出文本的模型，出错时主要增加沟通成本。一旦开始调用工具，问题的性质就变了：工具不是意见，是动作，动作接触真实世界。

只输出文本 调用工具
出错的后果 停在理解层面 文件被删、进程被中止、Git 历史被搞乱
风险类型 沟通成本 执行后果

所以工具系统最重要的问题只有一个：谁来约束这些工具。原文说，Claude Code 的回答是把工具变成受管执行接口，不让模型直接伸手碰世界。

受管执行接口（本页归纳）
  • 调度先按并发安全性分批，再执行（B）
  • 执行流程执行前后都有包裹层（C）
  • 权限allow、deny、ask 三态，授权与理解分开（D、E）
  • 中断停下也有专门语义（F）
  • Bash 特例最通用的工具受最严的看管（G）

本节是原文的观点，不涉及需要核对的事实。

B

工具调度属于行为宪法

原文 4.2

原文说，runTools() 不直接执行一串 tool_use，而是先按并发安全性分批。partitionToolCalls() 先读取工具的输入定义，再调用 isConcurrencySafe() 判断这类调用能否并发。能并发的归入并发批次，不能并发的拆成串行单元。

这看上去像性能优化，原文说它更接近一致性设计。一旦允许并发，就要回答一个老问题：上下文变化由谁决定、按什么顺序生效。原文说，Claude Code 在并发路径里先缓存 contextModifier，再按原始 block 顺序回放。最先完成的工具不能抢先改上下文，所以执行虽然并发，上下文演化仍有确定顺序。

原文的判断是：并发可以提高吞吐，但不能破坏因果秩序。成熟代理系统把并发当成需要证明自身无害的例外，而不是默认的自由。

实测：谁并发、结果按什么顺序回来

实验 结果 依据
一条回复里调用 Read、Read、Glob、Write、Write 三个只读工具同时运行；两个 Write 一个接一个 实测（第 1 章核对版）
一条回复里并行三个只读 Bash：慢的 find、快的 cat、ls 三个同时开始；下一次请求里的结果顺序是 cat、ls、find，即完成先后 实测
一条回复里并行两个 Bash：慢的 find、会失败的 cat cat 先失败，find 照常跑完；结果顺序是 cat、find 实测
事实核对
  • runTools()、partitionToolCalls()、isConcurrencySafe() 和原文给的文件位置（src/services/tools/toolOrchestration.ts）无法核对：源码不公开。文档没有写工具怎样并发。
  • “按工具属性决定并发还是串行”行为属实（实测）。
  • “上下文演化保持确定顺序”需要区分两件事。contextModifier 从外部看不到，无法核对。但 tool_result 本身也进入上下文，实测中它们按完成先后排列，不按调用顺序。第 1 章核对版里结果“按调用顺序”，是因为那次完成顺序恰好与调用顺序相同。
C

真正执行前已经发生了很多事

原文 4.3

很多人以为 tool_use 一出现，下一步就是执行。原文说，runToolUse() 依赖的执行逻辑已经接入 permission、hooks、telemetry、合成错误结果（synthetic error）。工具执行是一段完整的流程，包含四部分：

  1. 前置校验。
  2. 执行中事件。
  3. 执行后修正。
  4. 失败补偿。

工具的地位和普通库函数不一样。库函数属于程序内部，调用者自己承担后果；工具是模型与外部世界之间的接口，系统不能假设调用者判断稳定。原文说，包裹层这么多，是因为调用者本身就是最不稳定的变量。所以工具应该被建模为“需要运行时代为管理风险的外部能力”，而不是“模型能力的延长线”。接受这一点，permission、hooks、interrupt、synthetic result 就是常识，而不是负担。

D

权限先于能力

原文 4.4

原文说，权限入口在 useCanUseTool()。CanUseToolFn 的存在本身就说明：工具能否执行，不由模型自己说了算，而要交给权限判定链。hasPermissionsToUseTool(...) 返回三种结果：

  • deny：直接拒绝。
  • ask：进入协调器、swarm worker、classifier 或交互式审批路径。
  • allow：才真正放行。

成熟的权限系统除了“能”和“不能”，还要承认第三种状态：系统自己也不该替用户做决定。原文说，这从结构上否认了一种危险的想法：模型懂了用户意图，就等于有权代替用户执行。理解意图不等于拥有授权，更不等于拥有持续授权。系统必须把“会做”和“可以做”分开。

E

权限结果本身也是运行时语义

原文 4.5

原文说，PermissionResult 给 allow、deny、ask 准备了专门的描述函数。权限在 Claude Code 里不只是内部布尔值，而是有独立语义的运行时对象。

这件事重要，是因为系统要能明确地说出“为什么这一步没有继续”。代理说“我需要确认”，是在声明责任边界。边界说清楚了，后续的拒绝、放行、缓存规则、临时授权、永久授权才有地方安放。原文说，代理系统如果说不清“这一步能做、不能做，还是需要问”，就不该碰终端。终端不会替系统补完语义，只会执行。

实测：模型收到的拒绝说明各不相同

拒绝的原因 模型收到的错误结果
deny 规则命中（即使 hook 返回 allow） “Permission to use Bash with command rm HOOK-ALLOW.txt has been denied.”
ask 规则命中，-p 里没人批准 “Claude requested permissions to use Bash, but you haven't granted it yet.”
Manual 模式下的写文件命令没人批准 写明命令要创建或修改的路径，以及 Claude Code 为什么要先问
PreToolUse hook 返回 deny “PreToolUse:Write hook error: HOOK-DENY-PROBE”（hook 给的原因）
事实核对
  • PermissionResult 的描述函数和原文给的文件位置（src/utils/permissions/PermissionResult.ts）无法核对：源码不公开。
  • “权限结果有独立语义”行为属实（实测）。不同原因的拒绝，模型收到不同的说明；-p 的输出里还有 permission_denials 字段，列出被拒的调用。
  • 临时授权和永久授权有文档依据。在审批框里选 “Yes, and don't ask again” 后，Bash 命令的授权按仓库永久保存，改文件的授权到会话结束为止。
F

中断是一等语义

原文 4.6

工具一旦并发和流式执行，中断就变得复杂。系统面对的是一个有 queued、executing、completed、yielded 等多种状态的队列，而不是单一动作。

原文说，StreamingToolExecutor 是一个独立的流式工具执行器，重点是它怎样处理中断和丢弃：

  • streaming fallback 时，可以整体丢弃当前这批工具。
  • 按不同原因生成合成错误结果：sibling error、user interrupted、streaming fallback。
  • 专门判断中断原因：别的并行工具出错、用户打断、fallback 放弃当前批次。
  • 每个工具有 interruptBehavior，决定用户插话时是 cancel 还是 block。

原文说，Claude Code 不把中断看成“执行失败的特殊情况”，而是和执行本身同样重要的语义。系统不仅要知道工具能不能开始，还要知道它被打断时怎样收场、怎样补齐结果、是否允许新消息插入。这正是 Harness Engineering 的基本特点：不仅设计开始，也设计停下。

事实核对
  • StreamingToolExecutor、interruptBehavior、各种合成错误的名字，以及原文给的文件位置（src/services/tools/StreamingToolExecutor.ts），无法核对：源码不公开。
  • 流式执行行为属实：第 3 章实测中，模型回复还没结束，工具就已经开始运行。批处理那条路从外部分不出来。
  • 原图的“按安全顺序交出结果”和“确定的上下文”：两次实测中，并行结果都按完成先后进入下一次请求。所以 tool_result 的排列不是固定的；modifier 是否按块顺序回放，看不到。

  • 用户插话：文档说，排队的消息在工具调用结束后、同一轮内送达。按 Ctrl+Enter 立即发送时，能转后台的工作转到后台，不能转后台的就打断这一轮。这与 cancel、block 两种行为对应，但现版本多了“转后台”这一种。
  • 用户中断：第 3 章观察到 6 次真实中断，被打断的调用都拿到一条 is_error 结果，开头是 “The user doesn't want to proceed with this tool use”。CHANGELOG 也提到 -p 模式收到 SIGTERM 时，不再记录 “synthetic tool denials”，说明中断时会合成拒绝结果（旁证）。
  • subcommand 上限：实测在 Manual 模式下，用 allow 规则放行 echo，再运行 200 段 echo … && echo …。命令直接执行，没有请求批准，也没有被拒。文档只写到：解析不了的命令请求批准，超过 10,000 字符的命令总要批准。
G

Bash 为什么永远比别的工具更可疑

原文 4.7

原文说，Bash 不是普通工具，更像风险放大器，因为它太通用。越通用的接口，越难靠领域知识限制。读文件的工具不会顺手杀进程，grep 不会偷偷 push 代码，而 Bash 几乎什么都能做。Claude Code 从两层约束它：

层 原文说的内容 核对
prompt 对 git、PR、危险命令、hook、force push、交互式参数写了大量明确规则 !完整版全有；默认短版只剩交互式参数和用 gh 处理 PR
权限和安全判定 处理 shell 语义、命令前缀、重定向、wrapper、安全环境变量、分类器与规则匹配 ✓文档逐项都有说明
权限和安全判定 为了防止复合命令让检查失控，给 subcommand 数量设了上限 !实测 200 段没有触发；文档没有写上限

原文说，那段 prompt 看上去啰嗦，其实很有分寸：凡是后果大的地方，系统就不怕啰嗦。Bash 一直被当成需要特殊审查的危险通道。原文的判断是：高风险能力不应该享受通用能力的待遇；能力越通用，越要特殊看管。把 Bash 当成普通工具，往往只是设计上的偷懒。

事实核对
  • 原文给的文件位置（src/tools/BashTool/prompt.ts、src/tools/BashTool/bashPermissions.ts）无法核对：源码不公开。
  • prompt：实测完整版 Bash 说明约 10,700 字符，有 git 提交和 PR 两节。其中写了三类规则：“git push --force” 等破坏性操作要先考虑更安全的做法；“Never skip hooks (--no-verify)”；不要用 git rebase -i 这类交互式参数。默认短版约 2,100 字符，只剩交互式参数不支持、用 gh 处理 PR、用户要求时才提交或推送。
  • 权限判定：文档 permissions 页写明，Bash 规则识别 &&、||、;、| 等分隔符，每一段都要放行；会剥掉 timeout、nice 等 wrapper 和已知安全的环境变量赋值；deny 规则能匹配到任何一段；重定向单独检查。
  • subcommand 上限：见 F 的事实核对。论点“Bash 按特例治理”不受影响，依据换成上面的分隔符和 wrapper 规则。
H

工具系统也在保护系统自己

原文 4.8

权限、调度和中断看起来是在保护用户，其实也在保护系统自身。原文说，一个代理系统如果留下这些问题，最先崩掉的往往是它自己的一致性：

  • 不完整的 tool_result。
  • 失序的上下文修改。
  • 无边界的并发副作用。
  • 说不清楚的中断语义。

原文说，这一点在 query loop 和工具执行层是互相咬合的。前一章讲到，query loop 在中断时补齐合成 tool_result；这一章看到，StreamingToolExecutor 内部也有 discarded、hasErrored、siblingAbortController、interruptBehavior 等机制。两边一起作用，让系统在“执行过什么、没执行完什么、为什么停了”这些问题上，保持一条可追溯的因果链。这也是 Harness 的核心含义之一：替系统保住秩序。很多约束表面上防误操作，更深一层是防止系统变成一堆无法解释的状态残片。

事实核对
  • discarded、hasErrored、siblingAbortController 等名字无法核对：源码不公开。
  • “账本对齐”行为属实（第 3 章观察）。本机 104 个会话记录共 8,490 次工具调用，只有 2 次没有结果，都是文件里最后一次调用。
  • “失序的上下文修改”：tool_result 按完成先后排列（实测，见 B），但每条结果都带着对应调用的 ID，所以仍能追溯。

工具是受管执行接口；权限是代理系统的基本器官。

原文提炼的工程原则：

  • 模型提建议不等于拥有授权。
  • 并发要保持因果秩序。
  • 中断必须有一等语义。
  • Bash 这类高风险工具按特例治理。
  • 工具系统保护的既是用户，也是运行时本身。

核对后，五处证据都能换成文档或实测依据，论点成立。需要补充两点：

  • 并发的“因果秩序”在现版本靠调用 ID 维持，结果本身按完成先后排列。
  • 并发出错的处理比原文写时宽松：一个工具失败，其他工具照常完成。

下一章讨论另一种常见错觉：上下文越多越好。原文说，有经验的系统不会把上下文当仓库，而会把它当资源；第 5 章讲 memory、CLAUDE.md 与 compact 怎样共同组成上下文治理。
