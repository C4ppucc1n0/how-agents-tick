A

核心观点：工具是动作，必须有人约束

原文 4.1

只输出文本的模型出错时，主要增加沟通成本。一旦开始调用工具，问题的性质就变了：工具不是意见，是动作，动作会接触真实世界。跑错一条命令，文件会被删掉、进程会被中止、Git 历史会乱。

所以工具系统最重要的问题只有一个：谁来约束这些工具。Claude Code 的回答是把工具变成受管执行接口，不让模型直接碰世界。

普通库函数 工具
位置 程序内部 模型与外部世界之间的接口

所以工具不应被看作“模型能力的延长线”，而应被看作“需要运行时代管风险的外部能力”。接受这一点后，权限、hooks、中断、synthetic result 这些结构就是常识，而不是负担。

权限入口是 useCanUseTool()。模型提出工具请求后，系统不会默认执行，而是先调用 hasPermissionsToUseTool() 做权限判定，结果分成三种：

第三种状态 ask 很关键。成熟的权限系统除了“能”和“不能”，还要承认：有些决定，系统自己也不该替用户做。

权限链的三条不变式

不变式 含义
三态，不能简化成布尔值 结果只能是 allow、deny、ask 之一
无授权不得升级 ask 永远不会自动变成 allow
deny 不可翻转 同一个 tool_use 被拒后，不能重试成 allow

这套结构否认了一种常见而危险的想法：模型理解了用户意图，就有权替用户执行。理解意图不等于拥有授权，更不等于拥有持续授权。系统要把“会做”和“可以做”分开：模型可以提出动作，是否放行由运行时、规则和用户决定。

权限结果是运行时语义

PermissionResult.ts 给 allow、deny、ask 各准备了专门的描述函数。这说明权限在 Claude Code 里不是内部布尔值，而是有独立语义的运行时对象。

它的作用是让系统能明确说出“这一步为什么没有继续”。代理说“我需要确认”时，是在声明责任边界。边界说清楚了，后续的拒绝、放行、缓存规则、临时授权和永久授权才有地方安放。原文的说法是：连“能做、不能做、需要问”都分不清的系统，不该碰终端，因为终端不会替系统补完语义，只会执行。

中断是一等语义：StreamingToolExecutor

原文 4.6 · StreamingToolExecutor.ts

工具一旦并发、流式执行，中断就变得复杂。系统面对的不再是单个动作，而是一个多状态的队列：

StreamingToolExecutor 是独立的流式工具执行器。它这样处理中断和丢弃：

  • 整批丢弃：发生 streaming fallback 时，可以 discard 当前整个工具集合。
  • 按原因生成 synthetic error：区分三种原因：别的并行工具出错（sibling error）、用户中断、streaming fallback。
  • interruptBehavior：每个工具声明用户插话时该 cancel（取消）还是 block（继续跑完）。

并发与中断的失败矩阵

事件 前置状态 触发 下一步
并发批内单个工具失败 其他工具仍在执行 sibling error 其他工具照常；按 block 顺序回放 contextModifier
用户插话，工具设为 cancel 工具未完成 用户中断 取消执行，生成“用户中断”的 synthetic result
用户插话，工具设为 block 工具未完成 用户中断 工具跑到自然终点，期间阻塞新消息
streaming fallback 批次排队或执行中 fallback 丢弃整批，按顺序产出 fallback 的 synthetic result
abort 时有未完成的 tool_use 任意 abort signal 补齐 synthetic tool_result，让账本对齐
Bash 复合命令超过子命令上限 classifier 拒绝 安全检查 直接 deny，不进入 ask 路径

原文判断：Claude Code 不把中断当成“执行失败的特殊情况”，而是当成和执行同样重要的语义。系统不仅要知道工具能不能开始，还要知道被打断时怎样收场、怎样补齐结果、是否允许新消息插入。不仅设计开始，也设计停下，这是 Harness Engineering 的基本特点。

F

Bash 为什么永远更可疑

原文 4.7 · BashTool

Bash 不是普通工具，而是风险放大器，原因是它太通用。接口越通用，越难靠领域知识限制它。file read 工具不会顺手杀进程，grep 工具不会偷偷 push 代码，而 Bash 几乎什么都能做。

Claude Code 对 Bash 的不信任分两层：

对 Bash 的特殊治理
prompt 层BashTool 的 prompt.ts
  • git 与 PR 操作
  • 危险命令、force push
  • hook、交互式参数
权限与安全判定层bashPermissions.ts
  • shell 语义、命令前缀、重定向
  • wrapper、安全环境变量
  • classifier 与规则匹配
  • 子命令数量上限
  • prompt 层：对后果大的操作写了大量明确规则。看上去啰嗦，实际很有分寸：后果越大的地方，越不怕啰嗦。
  • 权限与安全判定层：为了防止复合命令让检查失控，还专门给子命令数量设了上限（对应 E 矩阵最后一行）。

原文的结论是：高风险能力不应享受通用能力的待遇。能力越通用，越要特殊看管。把 Bash 当成普通工具，往往只是设计上的偷懒。

（之前那篇《Bash 执行系统深度分析》，讲的就是第二层的具体实现。）

工具系统也在保护系统自己

原文 4.8

权限、调度和中断看起来是在保护用户，其实也在保护系统自身。系统如果允许自己留下下面这些问题，最先崩掉的往往是自己的一致性：

会破坏一致性的问题 本章对应的机制
不完整的 tool_result 中断时补齐 synthetic tool_result
失序的上下文修改 缓存 contextModifier，按原始顺序回放
无边界的并发副作用 按并发安全性分批，串行执行不安全的调用
说不清的中断语义 区分中断原因，用 interruptBehavior 声明怎样停

从源码提炼的第四个原则

原文 4.9
第四个原则

工具是受管执行接口；权限是代理系统的基本器官。

源码里有五处共同支持这个判断：

源码 做了什么 说明什么 详见
toolOrchestration.ts 先分批，再执行 调度先于冲动 B
toolExecution.ts 把 hooks、权限、telemetry、synthetic error 包在执行周围 执行不是裸调用 C
useCanUseTool.tsx 权限结果分成 allow / deny / ask 系统把授权当成独立语义 D
StreamingToolExecutor.ts 为中断、fallback、并发出错预留专门语义 停止和开始同样重要 E
BashTool 的 prompt.ts 与 bashPermissions.ts 对 Bash 采取特殊的高压治理 高风险能力必须接受更密的约束 F

提炼成五条工程原则：

  1. 模型提建议，不等于拥有授权。
  2. 并发要保持因果秩序。
  3. 中断必须有一等语义。
  4. Bash 这类高风险工具按特例治理。
  5. 工具系统保护的既是用户，也是运行时本身。
