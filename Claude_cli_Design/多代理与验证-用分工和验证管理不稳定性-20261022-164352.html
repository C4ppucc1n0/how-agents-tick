A

核心观点：问题从“会不会做”变成“怎么分工”

原文 7.1

任务一大，研究、实现、验证就挤在同一条上下文链上，抢预算、抢注意力、抢叙事中心。多代理看上去是自然答案，但并不便宜：不加约束的并行，只会把单代理的混乱复制几份。真正的难点是隔离各个 agent 的不稳定性，同时把结果组织回来。

Claude Code 没有把 subagent 当成“另一个会说话的窗口”，而是当成一段受管的执行流程。这段流程有四条边界要管：

子代理是受管执行流程
  • 缓存边界fork 时哪些参数必须和父代理一致（B）
  • 状态边界哪些状态默认隔离，哪些显式共享（C）
  • 验证职责综合由协调者负责，验证独立成阶段（D、E、G）
  • 清理责任生命周期可观测、可中止、可清理（F）

forked agent 的第一原则：不打烂缓存

原文 7.2 · forkedAgent.ts

forkedAgent.ts 开头的注释写明了 forked agent 工具的四项职责：

  1. 与父代理共享影响缓存的参数，确保 prompt cache 命中。
  2. 跟踪整个 query loop 的用量。
  3. 记录指标。
  4. 隔离可变状态，防止干扰主循环。

排在第一的是“共享缓存参数”。在 Claude Code 眼里，fork 是运行时层面的受控分叉，必须在意哪些参数要和父请求保持一致：

五项参数是：systemPrompt、userContext、systemContext、toolUseContext、forkContextMessages。源码还专门提醒：不要随便改 maxOutputTokens，因为它会影响 thinking 配置，而 thinking 配置也是缓存 key 的一部分。

原文的判断是：多代理首先是运行时经济学问题。子代理如果每次都把父上下文重新消耗一遍 token，看上去在并行提效，实际只是把浪费并行化。

状态隔离：子代理首先要减少污染

原文 7.3 · createSubagentContext()

createSubagentContext() 的默认行为是：所有可变状态都隔离，避免干扰父代理。

状态 默认做法 可选共享
readFileState（已读文件状态） 复制一份 —
abortController（中止控制） 新建一个子控制器，挂在父控制器下 shareAbortController
getAppState（读应用状态） 包一层，让子代理不弹权限提示 —
setAppState（写应用状态） 默认什么都不做 shareSetAppState
嵌套 memory 的相关集合 重新建空集合 —

另外，shareSetResponseLength 也属于需要明确选择才共享的回调。

为什么默认隔离？子代理最宝贵的地方，是不把自己的局部混乱污染主线程。这些局部混乱包括：

  • 研究中的误判。
  • 临时读到的文件状态。
  • 一次性推理分支。
  • 进行中的工具决策。

它们如果都直接写回主上下文，只会让主线程更快变脏。

Claude Code 的态度是：共享要靠明确同意，隔离是默认规则。只要是可变状态，就先隔离，再决定共享哪部分。

D

协调者模式：综合才是稀缺能力

原文 7.4 · coordinatorMode.ts

coordinatorMode.ts 规定了协调者的工作：

  • 帮用户达成目标。
  • 指挥 worker 做研究、实现和验证。
  • 综合结果，并和用户沟通。
  • 能直接回答的问题就直接回答，不要滥用委派。

最关键的一句是 Always synthesize（始终自己综合）：

协调者必须自己读懂研究结果，再写出具体的 prompt。不能说“based on your findings（根据你的发现）”，把理解继续外包给 worker。后续 prompt 里必须出现具体的文件、位置和变更。

原文认为这是多代理的命门。稀缺的不是并行输出。稀缺的是有人把 worker 掌握的局部知识，重新压成下一步行动，并且清晰、可执行、可验证。缺了这一层，多代理很快退化成礼貌的任务转发机。研究可以分布式，理解必须重新收束。

验证必须独立成阶段

原文 7.5 · coordinatorMode.ts

coordinatorMode.ts 把常见任务分成四个阶段：

它强调：验证的目标是证明代码有效，而不只是确认代码存在。源码里的要求几乎不留情面：

  • run tests with the feature enabled：在功能开启的状态下跑测试。
  • investigate errors, don't dismiss as unrelated：调查错误，不要当成无关问题打发掉。
  • be skeptical：保持怀疑。
  • test independently, don't rubber-stamp：独立测试，不要走过场盖章。

prompt 里明确分了两层：实现者自证，加上验证作为独立的质量关。

为什么重要？“我改了代码”和“代码因此正确”之间差得很远。模型尤其擅长在这中间搭纸桥。它会给出改动、解释，甚至像样的测试输出，但这些都不等于功能真的在系统里成立。把验证单列出来，就是防止“会改代码”冒充“能交付结果”。实现专注于改，验证专门怀疑这些改动站不站得住。

子代理不是扔出去就算了：hooks 与任务生命周期

原文 7.6 · hooksConfigManager.ts、LocalAgentTask.tsx

spawn 只是开头，收尾同样重要。子代理的生命周期由两套机制管理：

  • 生命周期 hook：启动时可以观测，停止前可以介入，转录路径可以追踪。“子代理结束”也是需要被管理的事件。
  • 异步任务注册（registerAsyncAgent）：每个异步 agent 都注册 cleanup handler，父任务中止会自动传给子代理。

这套机制关心四个问题：这个 agent 是否还在运行；父任务死了它是否该跟着死；它的输出文件还要不要保留；它的 cleanup 回调有没有泄漏。很多多代理 demo 只做到“能再起一个 agent”。Claude Code 把 agent 当作会泄漏资源、会残留状态、会在父任务结束后变成孤儿的运行实体来看待。

子代理崩溃 子代理异常退出 SubagentStop 退出码不为 0 清除输出，触发 stop hook exit 2 允许把 stderr 反馈回去继续跑

验证不只针对代码，也针对记忆和建议

放在多代理这一章里，它说明了一个更一般的事实：验证是整个系统抵抗时间漂移和上下文漂移的基本习惯。只验证新写的代码，却不验证旧记忆、旧假设、旧索引，系统仍会被历史信息带偏。

所以 verify 既是一项技能，也是一种组织纪律。工作可以分出去，信息可以存起来，其他 agent 可以先跑在前面；但在用户据此行动之前，总要有人回到当前现实，确认这些东西还是真的。

H

多代理真正解决的是不确定性的分区

原文 7.8

Claude Code 的多代理设计围绕一个朴素的目标：给不确定性分区。

分区的最大好处是职责清晰、错误可以定位：

环节 可能出的错
研究 漏了线索
综合 没吃透研究结果
实现 写错了
验证 放水

每一种错误都能被指认。单代理把所有事混在一起，出了问题只能整体返工。多代理真正的价值不是并发，而是把各类不确定性分别关进不同容器，再由协调者组织回来。

从源码提炼的第七个原则

原文 7.9
第七个原则

多代理依赖清晰分工：研究、实现、验证和综合各自处在不同约束容器里，最后由协调者把结果重新缝合成可交付结果。

源码在六个地方共同支持这个判断：

源码 做了什么 说明什么 详见
forkedAgent.ts 把缓存安全参数、用量跟踪和状态隔离放在第一位 fork 首先是运行时控制问题 B
createSubagentContext() 默认隔离可变状态，只允许显式共享 多代理先防污染，再谈协作 C
coordinatorMode.ts 要求协调者自己综合，而不是转发研究结果 综合理解不能外包 D
coordinatorMode.ts 把验证独立成阶段，要求独立证明变更有效 实现与验证必须角色分离 E
hooksConfigManager.ts 提供 SubagentStart / SubagentStop 生命周期 hook 子代理是可观测对象，不是黑箱线程 F
LocalAgentTask.tsx 处理父任务中止、cleanup、输出清除 agent 生命周期需要回收机制 F

提炼成六条工程原则：

  1. fork 先看缓存与状态边界，再谈角色分工。
  2. 子代理默认隔离，共享必须显式声明。
  3. 研究可以委派，综合不能外包。
  4. 验证必须与实现解耦，否则系统会奖励自证正确。
  5. agent 生命周期必须可观测、可中止、可清理。
  6. 并行的真正价值，在于职责更清楚。

下一章讨论这套机制落到团队里时，怎样从个人技巧变成组织制度。也就是 CLAUDE.md、skills、审批、hook、memory 怎样从“某个高手自己会用”，变成“团队可以稳定复用”的工程实践。
