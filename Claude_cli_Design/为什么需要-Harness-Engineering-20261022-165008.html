A

核心观点：问题在于让模型别乱来

原文 1.1

一个会说话的概率分布，一旦能接触 shell、Git、网络和本地文件，问题就从“回答得不够好”变成了“执行造成实际破坏”。

Harness Engineering 就是一套制度化控制平面。它把这样一个不稳定的核心部件，约束成可管理的系统。它要面对的现实只有一条：模型并不天然值得信任。忽视这一点，问题最后多半会出现在日志和事故记录里。

B

第一层：受约束的会话系统

原文 1.2 · constants/prompts.ts

表面上，Claude Code 像一个能对话、还能顺手改代码的 CLI。但从实现上看，它一开始就没把自己当成“裸模型接口”。它是一个会话系统，有上下文边界、运行时状态和行为规约。这一点从 system prompt 的组织方式就能看出来，它由三部分依次组成：

  1. 身份和总任务。
  2. 系统级说明：工具、权限、系统提醒、上下文压缩。
  3. 做任务时的工程约束：不越权改动，不把验证说成已完成，不为省事发明抽象。

很多人谈 prompt，还停在“你是一个什么样的助手”这种修辞层面。Claude Code 把 prompt 放进了运行时控制结构，用这些文字规定执行边界、失败行为和报告责任。

分段拼装

这个 prompt 是分段拼装的。getSystemPrompt() 把静态部分和动态部分明确拆开，动态内容按段注入：

buildEffectiveSystemPrompt() 再把默认 prompt、自定义 prompt、agent prompt 和追加 prompt 组织成一套优先级规则。

这说明一个朴素的工程事实：可用的代理系统不能靠一段“万能提示词”解决所有问题。它必须把控制拆成层，把层拆成职责。否则，新增的提醒和禁令很快会互相冲突，系统行为也会难以预测。

控制平面的三条硬约束

不变式 含义
身份不等于运行时 prompt 至少包含 default、project、custom、agent、append 这几层
工具受调度 每次工具调用执行前，由调度器决定它能否并发
错误进主路径 遇到可恢复错误时，只能走“恢复”或“干净地终止”

（三条分别对应第一、三、五层。）原文说，任何一条被越过，后面几章讲的 query loop、工具、上下文和恢复机制都会立刻显得可疑。

C

第二层：代理依赖持续循环

原文 1.3 · query.ts

prompt 规定系统应该成为什么样子，query loop 规定它实际上怎样运行。Claude Code 的核心不在某个单独的 API 调用，而在 query() 和 queryLoop()。

  • 跨迭代状态：messages、toolUseContext、autoCompactTracking、恢复计数、轮次计数等，都放进同一个跨迭代状态。这等于正式承认：上一轮留下的问题会进入下一轮，系统必须有能力继续处理。
  • 调用前的治理：每轮调用模型前，先处理消息裁剪、tool result budget、history snip、microcompact、context collapse、autocompact。共同目的是在调用发生前，尽量把控制权收回到运行时一侧。

这是 Harness 思维的核心：系统能不能在连续多轮里保持行为一致。具体要看四点：

  • 有没有预算概念。
  • 有没有恢复概念。
  • 上下文膨胀后有没有自救机制。
  • 工具调用失败后，能不能继续推进任务。

缺少这些结构，所谓智能体只是一个不稳定的执行者。

所以 Harness Engineering 不是 prompt engineering 的附属品：

prompt engineering Harness Engineering
关心 措辞 状态机
决定 表达效果 系统行为最终由谁负责
D

第三层：工具调用必须服从调度

原文 1.4 · toolOrchestration.ts

模型只能输出文本时，顶多让人觉得它有时说得太满。一旦能调用工具，风险就从修辞风险变成执行风险。这时最重要的问题是：谁决定工具怎么跑。Claude Code 的答案是：运行时根据工具属性决定并发还是串行。

这说明 Claude Code 没有把工具当成模型能力的自然延伸，而是当成需要调度纪律的受管执行单元。缺少调度纪律的工具系统，只会把模型的不稳定性放大到外部世界。

不受约束的并发会扩大事故半径。Claude Code 在这里采取偏保守的策略。在会碰到文件、终端和权限的场景里，这种保守通常更可靠。

E

第四层：最危险的工具配最细的规矩

原文 1.5 · BashTool/prompt.ts

所有工具里，Bash 最值得警惕。它几乎不受领域边界约束，能直接接触文件、进程、网络和 Git 仓库，还带着重定向、管道等复杂的 shell 语义。系统对 Bash 过度信任，后果通常会很具体。

BashTool 的 prompt 里写了一整段操作规约，尤其是 git 和 PR 部分：

  • 不要乱改 git config。
  • 不要跳过 hooks。
  • 不要随手 git add .。
  • pre-commit 失败后，不要用 --amend 把上一条提交也搭进去。
  • 没有明确要求时，不要提交。
  • 更不要默认 push。

有人会觉得这过于细碎，但高风险接口通常就需要高密度约束。Bash 一旦进入真实工作流，很多规则都必须明确写出来。

原文由此提出 Harness Engineering 的一条重要原则：把高风险能力包装成高约束能力，能力越强，控制越细。外部世界不会因为模型语气坚定，就原谅一次错误执行。

F

第五层：错误属于主路径

原文 1.6 · query.ts

很多软件把成功路径当正文，把失败路径当例外。代理系统不能这样，因为它的失败并非偶发，而是一直存在：

代理系统会持续遇到的失败
  • 上下文类超 token、prompt too long、max_output_tokens
  • 执行类工具被拒绝、hook 阻塞、API 重试
  • 交互类用户打断

（分类是本页归纳，条目来自原文。）

这些情况如果只在最后用几个 catch 打发，系统表面在运行，实际只是不断把麻烦往后推。Claude Code 的 query loop 没这样做。看 autocompact 的处理，以及上下文上限和阻断逻辑的注释，就能看出它把失败当成一种结构性条件，会持续发生。

普通助手 Harness
设计逻辑 先回答，错了再道歉 先约束，再执行
出错时 靠临场发挥补救 按恢复路径处理

会道歉的系统不一定成熟。更成熟的系统知道四件事：何时不该开始、何时该重试、何时该中止、何时该准确汇报失败。

从源码提炼的第一个原则

原文 1.7
第一个原则

代理系统的关键能力是约束执行。

源码在五个关键位置指向同一个结论：

源码 说明什么 详见
constants/prompts.ts prompt 是控制平面的一部分，而不是人格装饰 B
utils/systemPrompt.ts 系统行为必须有清楚的分层优先级 B
query.ts 代理运行依赖持续的循环状态，而不是单次问答 C
services/tools/toolOrchestration.ts 工具调用必须服从调度纪律 D
tools/BashTool/prompt.ts 高风险工具必须伴随高密度约束 E

放在一起看，Harness Engineering 并不神秘。它只是坚持几条常被忽视的工程常识：

  • 模型会犯错。
  • 工具会扩大错误后果。
  • 上下文会膨胀。
  • 状态会污染下一轮。
  • 用户会打断你。
  • 失败会反复出现。

既然如此，系统就不能靠“聪明”维持秩序，只能靠结构维持秩序。结构不像聪明那样显眼，但通常更可靠。

下一章讨论这套结构里最容易被误解的一层：system prompt。很多人把它看成人设文本，第 2 章会说明它更接近规章制度：人设可以改善观感，规章才能约束机器。
