核心观点：人设和控制平面不在同一层

原文 2.1

一说起 system prompt，很多人想到的是人设：你是谁、你擅长什么、最好再有一点稳定的人格。这对聊天系统够用，对要读文件、调工具、动 shell、跨轮执行的代理系统就不够了。

人设 控制平面
解决的问题 它像什么 它能做什么、什么时候做、做错了怎么办、谁来兜底
形态 一篇人物小传 一组分层拼装的行为区块
更接近 台词 运行时协议

Claude Code 的 system prompt 属于后者。

控制平面的五个方面

Prompt 控制平面
  • 分层prompt 是一组 section，而不是一段字符串（B）
  • 优先级多个来源按固定顺序装配（C）
  • 连接记忆CLAUDE.md 和记忆规则也进入 prompt（D）
  • 考虑缓存区分可缓存和会打破缓存的部分（E）
  • 可覆盖但有结构用户可以改内容，装配结构不变（F）

B

prompt 从一开始就是分层的

原文 2.2 · constants/prompts.ts

getSystemPrompt() 返回一个由多个 section 组成的数组，而不是一段完整字符串。prompt 一旦变成多个块，系统就承认了它内部有一组职责不同的约束。这些 section 至少包括三类：

system prompt 的 section
  • 身份与总任务
    • 交互式代理，用工具帮用户完成软件工程任务
    • 夹带安全约束，例如不要乱猜 URL
  • 系统级规则
    • 用户能看见哪些文本
    • 工具调用可能触发权限审批
    • 用户拒绝后不能机械重试
    • 工具结果和用户消息里可能混入 system-reminder
    • 上下文会被自动压缩
  • 做任务时的工程性指令
    • 不要随意增加需求
    • 不要越权优化
    • 不要为了显得完整而隐瞒验证失败
    • 不要在没必要时制造抽象

系统级规则不关心模型“像不像聪明助手”，而关心它是不是一个守规矩的执行体。这就是控制平面的语气：核心任务是定义边界。

工程性指令看起来像写作风格要求，其实和工程约束绑得很紧。一个会“顺手优化一切”的模型，从产品角度看也许很热情，从工程角度看却相当危险。

D

prompt 还连接着记忆系统

原文 2.4 · claudemd.ts、memdir.ts

在 Claude Code 里，prompt 是整个上下文治理的入口，而不只是“写给模型看的一段话”。

  • getClaudeMds()：把四种来源的内容整理成统一格式，再拼进 prompt 相关的上下文。每种内容都写明了来源。
  • buildMemoryLines()：把“怎样保存记忆”也写进 prompt。它告诉模型：memory 是文件化的持久系统；MEMORY.md 是索引，不是正文；frontmatter 怎么写；哪些信息不该保存；plan 和 task 不该被误用成 memory。

这一步把 prompt 的职责从“约束当前行为”扩展到了“约束未来知识怎样沉淀”。Claude Code 不只用 prompt 规定这一轮怎么说话，还用它规定长期记忆怎样形成。走到这一步，prompt 就不再是语气问题，而是制度问题。

控制平面还要考虑缓存与计算成本

原文 2.5 · systemPromptSections.ts

多数人理解 prompt 时很少想到性能。但 prompt 同时也是计算成本：越复杂、变化越频繁，缓存命中就越差，系统就越贵、越慢。Claude Code 把 prompt section 分成两类：

section 类型 缓存 说明
systemPromptSection 可缓存 resolveSystemPromptSections() 优先从缓存取，只在必要时重算
DANGEROUS_uncachedSystemPromptSection 会打破缓存 名字里的 DANGEROUS 提醒使用者它的代价

执行 /clear 或 /compact 后，clearSystemPromptSections() 会清空这些缓存状态。

用户可以覆盖 prompt，但不能跳过结构

原文 2.6 · main.tsx

Claude Code 没有把用户锁死在默认 prompt 上，CLI 明确支持覆盖和追加：

关键在于：无论用户怎样覆盖和追加，最终都由同一个 buildEffectiveSystemPrompt() 装配。系统允许自定义，但不放弃秩序；用户可以改内容，系统保留结构。

没有结构的可定制，最后往往退化成另一种随意。今天加一段，明天减一段，后天某个 agent 又替换掉基线约束，系统行为就越来越像临时口头通知。Claude Code 的选择是：允许修改，但修改必须发生在既定的优先级和分层机制里。

G

prompt 更像宪法，而不是台词

原文 2.7

台词是给角色在场上说的；宪法规定权力边界、责任关系，以及例外情况怎样处理。Claude Code 的 prompt 更接近宪法，因为它满足五个结构条件：

结构条件 而不是 详见
分层 一块写到底 B
有优先级 谁后写谁说了算 C
与 memory、CLAUDE.md、agent instructions、MCP instructions 一起组成控制平面 孤立的一段文字 D
有缓存和动态 section 机制 随手拼一段文本 E
和运行时紧密耦合 游离于系统之外的装饰物 B–F

所以，单独“写一个好 prompt”价值有限。更重要的问题是：prompt 在系统里处于什么位置，和哪些模块配合，是否参与权限、状态、上下文和长期记忆的治理。不回答这些问题，所谓好 prompt 往往只在某个顺利的场景里暂时成立。

从源码提炼的第二个原则

原文 2.8
第二个原则

Prompt 的价值，在于它是否被纳入一套清楚的控制结构。

源码在五个地方共同证明了这一点：

源码 做了什么 详见
constants/prompts.ts 把 prompt 写成分段的控制结构，而不是一段统一宣言 B
utils/systemPrompt.ts 明确规定 prompt 来源的优先级 C
utils/claudemd.ts 把项目级内容和长期记忆纳入上下文装配 D
memdir/memdir.ts 用 prompt 规定长期记忆的保存规则 D
constants/systemPromptSections.ts 把 prompt 变成可缓存、可失效、可按段重算的运行时对象 E

所以，成熟代理系统里的 prompt 不是“让模型入戏的开场白”。它更像一套运行中的制度文本。制度文本当然可以写得清楚，但最重要的始终是约束力。
