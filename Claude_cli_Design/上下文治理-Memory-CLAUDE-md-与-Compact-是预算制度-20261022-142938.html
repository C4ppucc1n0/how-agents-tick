A

核心观点：上下文是预算，不是仓库

原文 5.1

“信息越多，系统越聪明”是一个危险的神话。上下文不是“存进去就算拥有”的仓库，而是一笔昂贵、容易膨胀、会自我污染的预算。该加载什么、该截断什么、什么要长期保留、什么只能短期摘要，都是运行时要治理的事。

本章讨论的是：Claude Code 怎样防止自己被记住的东西拖垮。“记住更多”和“治理记忆”看起来相近，在工程上是两种制度。

本章涉及的五套机制

上下文治理
  • 长期规则CLAUDE.md 体系：分层加载的持久指令（B）
  • 长期记忆memdir：MEMORY.md 只做索引，正文放独立文件（C）
  • 会话连续性session memory：用固定模板记录“做到哪了”（D）
  • 窗口预算autocompact：预留空间、设缓冲、失败熔断（E）
  • 压缩后重建compactConversation：摘要后恢复工作环境（F、G）

（按寿命分层的说法来自原文 5.8 的工程原则。）

B

CLAUDE.md：长期规则和临场对话分开

原文 5.2 · claudemd.ts

claudemd.ts 把指令来源分成四层：

层 例子
managed memory /etc/claude-code/CLAUDE.md
user memory ~/.claude/CLAUDE.md
project memory 项目根目录的 CLAUDE.md、.claude/CLAUDE.md、.claude/rules/*.md
local memory CLAUDE.local.md

这些文件按优先级和目录距离加载：

  • 离当前工作目录越近的 project 规则，优先级越高。
  • 越私有、越本地的规则加载越晚，因此越靠近模型注意力的前沿。

为什么要单独做一套

团队规范、个人偏好、仓库约束的寿命，远长于某一轮用户消息。如果都塞进聊天记录，系统会在两个极端之间摇摆：要么每轮重复注入，浪费上下文；要么靠模型自己回忆，迟早失手。

claudemd.ts 的答案是把稳定规则做成可发现、可分层、可组合的持久指令系统。它支持 @include，但只允许明确列出的一批文本扩展名，防止有人把二进制文件、巨型文档或不该进 prompt 的东西带进来。

原文把这称为工程师的克制：先问清楚什么值得进入系统记忆，什么一旦进入就是污染。

MEMORY.md 是索引，不是日记本

原文 5.3 · memdir.ts

CLAUDE.md 管规则层，memdir 管更细的长期记忆。它的入口文件是 MEMORY.md，但这个文件被定义为索引，不鼓励直接堆内容。保存一条记忆分两步：

为什么这么麻烦？入口文件天然会被频繁加载，频繁加载的东西一旦变胖，整套上下文都会被它拖慢。所以“入口必须短”被做成了硬约束：超出上限时，truncateEntrypointContent() 直接截断，并警告“只加载了一部分，请把细节移到 topic files”。

原文从这里抽出的原则是：长期记忆必须分成“入口”和“正文”。

入口（MEMORY.md） 正文（topic 文件）
职责 低成本寻址 高密度承载
加载 频繁加载 需要时再读
约束 200 行、25,000 字节 没有入口那样的硬上限

入口一旦既当目录又当正文，就会失效，整套记忆系统随之退化成摆设。

D

Session memory：短期连续性也要结构化

原文 5.4 · SessionMemory/prompts.ts

只有长期记忆还不够。代理系统真正难的，常常是“这轮之前我们做到哪一步了”，也就是一次会话内部的连续性。Claude Code 为此建了一套笔记模板：

session memory 默认模板
  • Current State现在做到哪了
  • Task specification
  • Files and Functions
  • Workflow
  • Errors & Corrections踩过的坑和修正
  • Codebase and System Documentation
  • Learnings
  • Key results
  • Worklog

更新笔记的 prompt 有五条明确要求：

  • 只能用 Edit 工具更新笔记文件。
  • 不要提“记笔记”这件事本身。
  • 不要改模板结构。
  • Current State 必须始终反映最近的工作。
  • 每节都要信息密集，同时控制预算。

预算是硬数字：每节最多 2,000，总量最多 12,000 tokens。超出时，系统要求大幅压缩，并优先保留 Current State 和 Errors & Corrections（上图加星的两节）。

所以 session memory 不是“另存一份聊天记录”。它把当前会话提炼成一份可以继续工作的操作说明，不求完整复刻对话，只保留继续干活必需的骨架。上下文预算是工作内存，工作内存的第一职责是可操作。

自动 compact：上下文治理首先是预算治理

原文 5.5 · autoCompact.ts

有了长期规则、持久记忆和 session memory，上下文还是会膨胀。只要对话够长，总会逼近窗口边缘。autoCompact.ts 承认这个现实，并提前留出余地：

  • 先预留摘要的输出空间：compact 本身也要花 token，系统不会等窗口快用完才想起压缩。
  • 再扣一层缓冲：警告阈值、错误阈值、手动 compact 也各有自己的缓冲。

原文的道理是：上下文治理要提前为失败和恢复留出余地。不留余地的系统，平时看着节俭，其实是把风险留给了下一轮。

失败熔断

autocompact 被当成一段会被追踪、会失败、会被限流的运行时行为。它的跟踪状态除了“是否压缩过”，还记录轮次计数、轮次 ID 和连续失败次数。

源码注释写明了原因：全球每天曾有大量 API 调用浪费在连续失败的 autocompact 上。系统可以失败，但不能无限次、无记忆地失败。

名称 值 作用 位置

F

compactConversation：重建可继续工作的上下文

原文 5.6 · compact.ts

compact 不只是“把前面的聊天摘要一下”。compactConversation() 把原有上下文拆开、摘要，再注入必要的附件，重新搭出一个还能工作的环境。

压缩前清洗

  • stripImagesFromMessages()：把图片、文档换成 [image]、[document] 这样的标记。
  • stripReinjectedAttachments()：剥掉之后反正要重新注入的附件，免得浪费 token。

两步都在丢掉“对摘要没用、但 token 开销很大”的部分。

摘要失败的处理

truncateHeadForPTLRetry() 专门应对“compact 请求自己都 prompt too long”的情况。系统不仅承认主流程会爆，也承认救火工具本身会爆。

压缩后重建

成功后，系统不是只留一条摘要，还会做这些事：

类别 动作
文件 清空旧的 readFileState，重新生成压缩后的文件附件
计划 补回 plan 附件和 plan mode 附件
技能与工具 补回 invoked skills 附件；补回 deferred tools、agent listing、MCP instructions 的增量附件
hooks 执行 session start hooks 和 post-compact hooks
边界记录 写入 compact boundary 消息，记录压缩前的 token 数和边界信息

（分类是本页归纳，动作来自原文。）

这些动作说明，compact 的目标是把“继续干活所需的运行时环境”重新铺平，摘要只是中间产物。原文把它比作一次受控重启。很多系统只做前半截。压缩后它们记得前面聊过什么，却丢了工具、计划和附件状态，还得再花几轮找回自己。

G

关键是保住工作语义

原文 5.7

compact.ts 的后半段有一个贯穿始终的倾向：保住工作语义。

  • 恢复最近访问文件的附件：这些文件构成当前工作面的局部现实。
  • 恢复 plan mode：否则模型压缩完可能忘了自己还在 plan 模式的约束里。
  • 保留 invoked skills，但每个 skill 有 token 上限：防止 skill 在压缩后喧宾夺主。

源码里有一句话：per-skill truncation beats dropping。即使要裁，也优先保住开头最关键的指令，而不是整个扔掉。原文的说法是：纯节流是砍，治理是知道该砍哪里、该保什么。

由此得到经验：优先保留能维持行动语义的内容，而不是看起来信息量最大的内容。

优先保留 不必占着位置
文件细节 冗长的历史对话
当前计划 重复出现的附件
错误修正 运行时随时能重新拿到的东西
技能约束

从源码提炼的第五个原则

原文 5.8
第五个原则

上下文是工作内存。治理它的目标是支持系统继续工作。

源码在五个层面共同支持这个判断：

源码 做了什么 说明什么 详见
claudemd.ts 把长期指令分层加载 稳定规则要和临时对话分开治理 B
memdir.ts 把 MEMORY.md 定义成索引，并强制截断 入口文件必须短，而且可寻址 C
SessionMemory/prompts.ts 用固定模板提炼会话连续性，给单节和总量设预算 短期记忆也必须结构化 D
autoCompact.ts 为 compact 预留输出预算、缓冲区和失败熔断 上下文窗口要按风险来经营 E
compact.ts 摘要后恢复计划、文件、技能、工具附件和 hook 状态 compact 的目标是重建工作语义，不是写一段好看的总结 F、G

提炼成五条工程原则：

  1. 长期规则、长期记忆、会话连续性分层，不混写。
  2. 入口型记忆必须短小。
  3. session summary 为“继续工作”服务，不追求“回忆完整”。
  4. compact 是主路径，不是异常。
  5. 压缩后必须保住运行语义。

下一章讨论这套治理碰到极限时怎么办：prompt too long、max output tokens、hook 死循环、恢复分支互相打架。到那时才看得出，一个代理系统是在“赌不出事”，还是认真设计了出事之后怎样继续运行。
