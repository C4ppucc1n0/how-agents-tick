A

核心观点：agent 靠循环，而不是一问一答

原文 3.1

把会写代码的模型当成加强版问答接口，是最常见的错误。系统一旦开始调用工具、跨轮执行、处理中断、保存状态、压缩上下文，“一问一答”就失效了。

在源码里，query() 只是一层壳，真正的核心是 queryLoop()。原文用 lifecycle（生命周期）概括这一点。一个系统能否称为 agent，不在于它会不会说，而在于几轮之后它还知不知道自己在做什么。

B

状态属于主业务

原文 3.2

很多系统把状态当成包袱，认为无状态更优雅。但代理系统一进入真实工作流，状态就会自然出现。忽视状态并不能消除它，只会让它以更难管理的方式回来。

Claude Code 把 query loop 的可变状态明确定义为 9 项（按用途归类）：

State
对话与工具messages、toolUseContext
压缩与恢复autoCompactTracking、maxOutputTokensRecoveryCount、hasAttemptedReactiveCompact
轮次与流转turnCount、transition、stopHookActive、pendingToolUseSummary

每次 query loop 启动时，这些状态被整体装配成一个 State 对象，之后在每个 continue 分支里整体更新。恢复、压缩、预算、hook、轮次计数没有散落在局部变量里，因为它们共同决定“本轮结束后，下一轮如何继续”。

脚本只关心这一步有没有跑完。代理系统还要关心：这一步失败后，下一步能不能接住前面留下的状态。

原文认为，这串顺序本身就是一种架构声明：Claude Code 把上下文治理放在模型推理之前。它不把“从混乱中整理秩序”的责任交给模型，而是由运行时先整理好，再把更干净的输入交给模型。

很多系统的做法相反：先把大量上下文塞进去，再指望模型自己判断什么重要。这看似省事，实际上是把运行时该承担的责任转嫁给了概率分布。

D

调用模型只是循环的一段

原文 3.4

治理完成后才进入模型调用。这里的关键细节是：系统用 for await 流式消费模型输出，而不是同步拿回一个完整结果。所以模型输出在 Claude Code 里是一串事件，事件可能是 assistant 文本、tool_use block、usage 更新、stop reason 或 API 错误。

一旦把模型输出当成事件流，架构就不再是“请求-响应”，而是“驱动-调度-反馈”。流式输出的意义不只是早点看到几个字，而是让运行时在模型还没结束时，就开始安排下一步执行。

所以原文说，心跳是整个循环，而不是模型调用本身。循环要管的是：输入怎样收进来，流怎样消费，工具怎样调度，失败怎样恢复，何时继续下一轮。

E

心跳必须能处理中断

原文 3.5

一个循环不仅要能持续运行，还要能在必要时停下来。停不下来，系统就只剩惯性。

背后的原则是：系统一旦对外承诺了一段执行，中断时就要把账补平。不能因为用户打断了，就假装前面的 tool_use 从未发生。

外部系统、UI 和 transcript 都需要一条一致的因果链。哪怕结果是“中断了”，也要中断得完整。代理系统进入多工具、多轮次之后，外界要求的不只是“有没有最终答案”，还有“留下的轨迹能不能解释”。解释不了的轨迹，迟早会变成运维问题或审计问题。

F

心跳还必须能恢复

原文 3.6

中断是外部打进来的意外，恢复是系统内部预留的余量。没有恢复能力的循环，等于把幸运当成了设计。Claude Code 的恢复是层层递进的，不是简单重试。最典型的两种情况如下。

prompt 太长（prompt-too-long）

系统先判断最后一条 assistant message 是否是被暂扣（withheld）的 prompt-too-long 错误。恢复手段按成本和破坏性从低到高逐层尝试。

输出超长（max-output-tokens）

续写的要求是从被截断处接着做，而不是先道歉、先总结。

原文评价：Claude Code 把恢复看成运行时主路径的一部分，而不是模型失败后的礼貌动作。恢复的意义是给系统一个继续工作的机会。

G

停止条件不能只有一个

原文 3.7

问答系统有回答就结束。代理系统不行：“当前轮结束”不等于“任务完成”，更不等于“系统成功”。queryLoop() 至少区分了下面这些情况：

事件 前置状态 触发 下一步
流正常结束，有 tool_use 有未完成的 tool_use stop reason follow-up，进入工具执行
流正常结束，无 tool_use 没有待处理的工具 stop reason 进入 stop hooks
用户中断 任意 abort signal 消费剩余结果，生成 synthetic tool_result
prompt 太长 还没试过 compact 可恢复错误 走 collapse 或 reactive compact
输出超长 上限未到最大 stop reason 提高上限后重跑
输出超长 上限已到最大 stop reason 追加 meta 消息，续写
stop hook 阻塞，且 prompt 又太长 已试过 reactive compact 两次失败 跳过 stop hooks，报告错误
API 错误 — api_error 直接返回，不重试

H

QueryEngine：循环属于会话生命周期

原文 3.8

QueryEngine 的源码注释直接写明了它的职责：

QueryEngine owns the query lifecycle and session state for a conversation.

也就是说，它管理的是一整个对话的生命周期，而不是某一次调用。一个 QueryEngine 对应一个对话；每次调用 submitMessage()，都是在同一个对话里开始新的一轮，状态持续保存。

query loop 是会话系统真正的执行中心，UI、SDK 和 session persistence 都围着它转。所以要理解 Claude Code，不能只看它有哪些工具、prompt 写了什么，最终要看这个循环怎样把各种约束落实成连续的行为。
