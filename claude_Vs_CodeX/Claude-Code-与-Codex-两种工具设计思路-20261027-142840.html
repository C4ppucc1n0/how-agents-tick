同一个任务的两条路径

任务：在项目里找到 print("hi")，改成 print("hello")。

  • Claude Code 每一步是一次独立的工具调用。Harness 在每一步检查参数和前置条件。
  • Codex 开了代码模式后，模型写一段 JS，在里面连续调用多个子工具。一次 exec 可以走完整条路径，但不保证成功。

一次 exec 出错了怎么办

结论

一次 exec 不保证成功。它只是把几步打包成一次往返。出错后，模型读完整输出，再写下一段 exec 修正。

exec 结果 触发条件 返回给模型的内容 你的记录中
Script completed 脚本正常跑完。命令退出码非 0 也算这一类 全部输出，包括命令的报错 1899 次，占 96.1%
Script failed 脚本抛出异常，例如 JS 语法错误、补丁对不上 失败前已有的输出，加上错误信息 31 次，占 1.6%
Script running 超过等待时间，脚本仍在运行 一个 cell ID，之后用 wait 取结果 44 次，占 2.2%
用户中止 你手动打断 中止时间 3 次，占 0.2%

你的 Codex 记录说明了什么

  • 平均每轮对话调用 10.5 次 exec，中位数是 7。只有 16% 的轮次一次 exec 就结束。
  • 有 173 次输出带非 0 退出码，脚本状态却是 completed。命令失败不会让脚本失败，结果作为普通输出返回。
  • 输出出现错误字样后，68% 的下一步是再调用 exec，27% 是先给你回一条消息。

打包执行的风险

  • 命令失败不抛异常。如果脚本不检查退出码，后面几步会照常执行。
  • Claude Code 每步单独返回。第一步出错，模型马上就能看到，不会继续执行后面几步。代价是往返次数更多。
统计说明

状态和次数来自你本机 1977 条 exec 输出的首行。"错误字样"用正则匹配，是近似值。"补丁对不上会让脚本失败"是从记录推断的，源码中没有找到明确说明。

设计思路对比

维度 Claude Code Codex
核心假设 用结构化工具约束模型的行为 模型已经会用终端，给它通用执行能力
能力从哪来 工具说明和参数 schema 模型训练：补丁格式、终端使用习惯
安全边界 每次工具调用前检查权限 操作系统沙箱限制读写范围和网络
权限粒度 细：按工具、按命令前缀 粗：按目录和网络，越界时整体提权
上下文开销 工具说明多，用 ToolSearch 延迟加载 工具说明少，代码模式把多步合成一次调用
输出控制 工具自带分页和条数上限 模型自己用 head、sed -n 控制
跨平台 专用工具在各系统行为一致 受 shell 差异影响，例如 PowerShell 的引号规则
界面展示 diff 视图、可点击的文件路径 显示命令和输出

各自的代价

  • Claude Code：工具说明占上下文，模型要在多个工具里做选择。Bash 不支持交互输入。分类器可能误拦正常操作。
  • Codex：命令容易遇到引号转义和平台差异。输出容易过长。改文件依赖模型熟悉补丁格式。权限粒度较粗。
H

两边在互相靠近

  • Claude Code 在放宽：自动模式允许直接用 cat、grep、sed 读文件和做小改动。Workflow 工具让模型用 JS 脚本编排多个子代理。
  • Codex 在削减专用工具，同时增加协作工具：第三方资料称 0.117 删除了 read_file、grep_files。它又加入了 request_user_input、spawn_agent、tool_search。

如果你自己设计 agent 的工具

  1. 模型没训练过的格式，用结构化专用工具。
  2. 把沙箱当作底线，再用工具级权限做细分。
  3. 工具数量多时，先只给名字，用到再加载 schema。
