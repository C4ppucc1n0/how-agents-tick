5.2 Claude Code：把局部制度做成现场记忆

做什么：原文说，Claude Code 把地方化能力落在四样东西上，组合起来有“现场经验沉淀”的味道。

机制 原文说它做什么 核对
CLAUDE.md 说清这个仓库、目录、团队的常识 ✓成立
skill 打包工作流 ✓成立
hook 挂在生命周期上 ✓成立
session memory 让当前工作不必每轮重新做人 无法核对：文档里没有这个名字

怎么做：原文说，这些机制的共同特点是贴近任务现场。规则进入当前会话，参与当前执行，而不是先定义一套万古不变的制度。

为什么：原文认为，这种做法很实用，适合多项目、多目录、多约束并存。代价是：如果不额外整理，知识容易以“现场补丁”的方式扩张。原文的比方是一个随身带笔记本的工程师，走到哪就把当地规矩抄下来。

事实核对
  • CLAUDE.md 有四个位置：组织托管、用户、项目、本地。目录树上层的文件在启动时加载，子目录的按需加载。.claude/rules/ 还能按文件路径限定规则。
  • “不是制度”有文档依据：文档说 CLAUDE.md 和 auto memory 是上下文，“not enforced configuration”；要强制拦截，得用 PreToolUse hook。
  • hook：文档列出 33 个事件，分三种节奏：每个会话、每一轮、每次工具调用。
  • session memory：无法核对。文档里对应的机制是 auto memory：Claude 把纠正和偏好记进 MEMORY.md，每次会话开始加载前 200 行或 25KB。它跨会话保存，不只管当前会话。观察：本会话的系统提示里就有 auto memory 的使用说明。

5.3 Codex：把局部制度做成结构化注入和事件系统

做什么：原文说，Codex 也有 skill、本地规则和 hook，但更制度化。

怎么做：原文分三项讲。

  • skill：skills/src/lib.rs 把系统 skill 装到 CODEX_HOME/skills/.system，并打上指纹。install_system_skills() 比对指纹，只在 marker 不一致时才重写。原文由此说，skill 不是临时读入的文本，而是被安装、被管理、可追踪版本的资产。
  • AGENTS.md：不只是“读一份本地说明”，还带作用域和层级。局部规则不只是内容，还带位置关系。
  • hook：hooks/src/engine/mod.rs 把事件分开，每个 handler 都有事件名、matcher、timeout、状态提示、来源路径和显示顺序，接近一个显式的生命周期事件系统。引擎还分 preview_* 和 run_* 两条路径，先预览再执行。

原文还说，Codex 在 Windows 上因为支持不完整，明确关闭 codex_hooks 并返回 warning。hook 能不能开、为什么不开，都希望可以解释。

为什么：原文认为，把规则做成资产和事件，规则就能被安装、追踪和解释。

事实核对
  • install_system_skills() 成立，但只管打包在程序里的系统 skill。指纹是内容的哈希值，不是版本号。用户、仓库、管理员和插件的 skill，都从各自的目录直接读取。
  • AGENTS.md 的作用域成立。Codex 默认的 base instructions 写明：作用域是文件所在目录的整棵子树，嵌套越深越优先。
  • hook 事件已过时：当前有 14 个，原文只列了 5 个。
  • handler 的字段成立。此外每个 handler 还记录来源（system、user、project、MDM、plugin 等）和类型（命令或 MCP 工具）。
  • preview 和 run 两条路径成立。preview 只算出要跑哪些 handler，用来先发“hook 开始”事件；run 才真正执行。
  • Windows 上关闭 hook 已过时。当前开关名是 hooks，codex_hooks 只是旧别名；它处在 Stable 阶段，默认开启。hook 的运行代码里有 Windows 专用的进程处理。
  • “可以解释”的论点仍有别的依据：每个 hook 都带信任状态，取值为 managed、untrusted、trusted、modified。同一层配置里，hooks.json 和 config.toml 同时有 hook 时，Codex 给出 warning。

5.4 Claude Code 偏经验收编，Codex 偏制度挂载

做什么：原文把两边的本地治理方式放在一起比。

Claude Code：经验收编 Codex：制度挂载
规则去哪 现场经验不断收编进主循环附近 地方规则挂到明确的控制面和生命周期机制上
擅长 让 agent 在当前上下文里迅速学会“这里怎么办事” 让规则被分类、排序、安装、触发
原文的比方 熟悉现场、懂看气氛的老员工 制度意识极强的新项目经理，先把规则贴出来再协调人做事
事实核对
  • 两边的 hook 机制高度相似，不能作为这组对比的依据。Codex 的 hook 引擎类型名叫 ClaudeHooksEngine。它接受 Write、Edit、Agent 作为 matcher 别名，代码注释写明是为了兼容 “Claude Code-style names”。它还给插件设置 CLAUDE_PLUGIN_ROOT，注释写明 “For OOTB compat with existing plugins”。
  • Claude Code 的 hook 同样有事件、matcher、timeout、statusMessage，还能用 if 按权限规则过滤。两边的 Stop hook 都带 stop_hook_active 和 last_assistant_message。
  • “分类、排序、触发”在两边都有。“安装”在 Codex 只针对内置系统 skill；Claude Code 的插件也是安装的，还可以固定版本。
  • 仍有依据的差别在 AGENTS.md：Codex 在默认 prompt 里写明了作用域和优先级。Claude Code 的 CLAUDE.md 只是拼接。文档说，用户规则和项目规则冲突时，Claude 可能遵循其中任何一条。

5.5 对组织可复制性的影响

做什么：原文讨论两种做法在组织里能不能复制。

主要靠现场经验注入 主要靠结构化注入和事件挂载
长处 适应新仓库更快，在复杂的局部语境里更有效 组织扩展潜力大：规则容易统一分发、版本化和审计
代价 复制到更多团队需要额外整理，否则各写各的 CLAUDE.md、各做各的 skill，像各省自印教材 学习成本更高，团队要先接受更多显式制度

为什么：原文说这是经典取舍：越贴近现场越有弹性，越制度化越容易复制。真正决定结果的，是团队需要哪一种稳定性。

事实核对
  • 这组取舍是原文的观点，不核对。但它依赖的一个事实要修正：Claude Code 也有统一分发和版本化的手段。
  • 统一分发：组织可以部署托管 CLAUDE.md，开发者排除不掉；还可以在托管设置目录里放企业 skill。
  • 版本化：插件把 skill、agent、hook、MCP 服务器打成一个单元，从 marketplace 安装；插件可以写 version 固定版本。
  • 管控：托管设置能只允许托管的 hook（allowManagedHooksOnly），也能禁止用户和项目自带的 skill、agent、hook 和 MCP 服务器（strictPluginOnlyCustomization）。
  • Codex 同样有组织层：hook 的来源包括 MDM 和云端托管配置，skill 也有管理员目录。

5.6 本章结论

原文的结论，单独成节

Claude Code 更倾向于把局部治理做成现场记忆与运行时注入，Codex 更倾向于把局部治理做成结构化资产与生命周期事件系统。

原文说，这不是“都支持 skills 和 hooks”的同义反复。差别在于两边问的问题不同：

  • Claude Code 问：怎样让 agent 在这里干活更像本地人。
  • Codex 问：怎样让本地规则进入一套可管理的制度框架。

证据（已按事实修正）

  • 结构化资产：只对 Codex 的内置系统 skill 成立。其余 skill、AGENTS.md 和 hook 配置都从目录读取（章首图、5.3）。
  • 生命周期事件系统：两边都有。Codex 的 hook 引擎明确兼容 Claude Code 的配置写法（5.4）。
  • 现场记忆：CLAUDE.md 和 auto memory 确实作为上下文生效，不强制执行（5.2）。
  • 可管理的制度框架：两边都有组织级下发和管控（5.5）。
  • 仍有依据的差别：Codex 明写了 AGENTS.md 的作用域和优先级（5.3、5.4）。

原文提炼的工程原则

  • 通用 agent 要落地，就必须能吸收公司、仓库、目录和个人的局部制度（5.1）。
  • 越贴近现场越有弹性，越制度化越容易复制；关键是团队需要哪一种稳定性（5.5）。

下一章讲两种系统在更高风险处怎样分工：多代理、验证、持久状态和恢复。原文说，系统一旦让多个代理干活，光讲规矩不够，还得讲责任分离。
