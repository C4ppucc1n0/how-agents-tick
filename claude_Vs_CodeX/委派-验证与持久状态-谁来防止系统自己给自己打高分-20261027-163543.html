6.1 多代理的真正问题是责任

做什么：原文说，一听多代理就想到效率提升，其实真正棘手的是多出来的责任怎么切。同一个系统既执行、又总结、又验证，还顺手给自己写评语，结论多半令人宽慰但不可靠：“干得不错”。

怎么做：原文说两边都在切分责任。

多代理要切开的责任原文列举，示意
explore探索
execute执行
synthesis汇总
verification独立复核，“完成”不由执行代理自己宣布

  • Codex：也走这条路。tools/src/lib.rs 里有 create_spawn_agent_tool_v*、create_wait_agent_tool_v*、create_send_message_tool、create_close_agent_tool_v*，说明委派是正式的工具能力，不是黑魔法。

6.6 本章结论

原文的结论，单独成节

Claude Code 的多代理设计更强调运行时职责分离与现场收尾，Codex 的多代理设计更强调工具化委派、状态承接与可审计协作。

原文说，二者都试图避免系统自己给自己打高分：

  • Claude Code 更靠角色分离和验证纪律。
  • Codex 更靠显式接口、线程状态和协作记录。

证据（已按事实修正）

  • 工具化委派：成立。Codex 的委派是两套有 schema 的工具，当前默认是 v1（6.3）。
  • 状态承接：成立。子代理是独立线程，有七种状态；委派调用写进 rollout（6.3、6.5）。
  • 可审计协作：成立，但原文的故障矩阵多处要改。超时不关闭子代理，也没有强制回收句柄（故障矩阵）。
  • 角色分离：部分成立。Claude Code 有探索和执行两种子代理，没有内置的汇总和验证角色（6.2）。
  • 验证纪律：有依据，但落在 /verify 这类 skill 上，不在独立的验证代理上（6.2）。
  • 现场收尾：有 SubagentStart、SubagentStop hook 和停止后台子代理的手段；abort 传播的内部机制无法核对（6.5）。

原文提炼的工程原则

  • 多代理的真正问题是责任怎么切，而不是效率（6.1）。
  • “完成”不应由执行代理自己宣布（6.1）。
  • 验证要有状态承接，否则会沦为缺材料的表演（6.4）。
