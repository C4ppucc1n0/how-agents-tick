事实核对
  • Claude Code 一侧：partitionToolCalls、并发分批和执行器的状态名无法核对。源码不公开，官方文档也没有写工具并发。能对上文档的是：权限规则按 deny → ask → allow 的顺序生效，PreToolUse hook 在权限提示之前运行。

4.1 真正危险的是开始执行

做什么：原文说，模型说错话只浪费时间，跑错命令就可能把目录、仓库、进程和工作流一起带坏。真正把 AI coding system 区分开的，是调工具之前谁拥有最后解释权。

怎么做：两边都很认真，但认真得不一样。

Claude Code Codex
工具首先是什么 运行时调度纪律里的一环 类型化接口：先是规范化 API，其次才是执行单元
关心的问题 能不能跑、怎么跑、能不能并发、用户有没有拒绝、如何中断、结果怎么回到上下文 工具有哪些参数、审批怎么表达
原文给的源码 toolOrchestration.ts、toolExecution.ts、StreamingToolExecutor.ts、useCanUseTool.tsx、Bash 专门 prompt、allow / deny / ask 语义 tools/src/lib.rs 导出工具构造器；local_tool.rs 定义 exec_command、shell、shell_command、request_permissions 的 schema

为什么：原文认为，工具调用才是后果发生的地方，所以秩序要放在动手之前。

事实核对
  • Claude Code 的源码文件名无法核对：源码不公开。allow / deny / ask 三类规则有文档依据。
  • 当前 Codex 代码里没有 local_tool.rs。exec_command、write_stdin、request_permissions 的 schema 在 core/src/tools/handlers/shell_spec.rs。shell 和 shell_command 已不再定义成工具，shell_command 只作为保留名出现。
  • tools/src/lib.rs 导出的是 ToolSpec、JsonSchema 这些通用类型，以及把 MCP 工具、动态工具转成 API 工具的函数。具体工具的构造函数在 core 里。

4.2 Claude Code：重点在运行时编排和危险动作约束

做什么：原文说，Claude Code 的工具系统有很强的现场调度感。它承认工具调用是“一个带后果的过程”，不是单点动作。

怎么做：原文列出这些运行时职责：

  • 并发：看 schema 和 isConcurrencySafe()，决定先做哪个、哪些并行、哪些串行。
  • 顺序：会修改上下文的工具，要保证回放顺序稳定。
  • 流式执行：处理中断、synthetic result 和 UI 反馈。
  • 收尾：做完怎么记账，中途被叫停怎么办。
  • Bash：对 Bash 这类高风险工具反复提醒。

为什么：原文把它比作给模型装一个工地监工。对 Bash 的“唠叨”，是成熟工程对危险接口的态度。

事实核对
  • 并发分批、回放顺序、synthetic result：无法核对。源码不公开，官方文档没有描述工具怎样并发。
  • 中断：成立。文档写明，按 Esc 时 “The running tool call is canceled”。
  • 对 Bash 的专门约束：成立。文档写明 Bash 规则怎样拆分复合命令、剥掉 timeout 这类包装命令、放行哪些只读命令。观察：本会话的 Bash 工具说明也带有大段专用指引。

做什么：原文说，Codex 把“风险动作”的控制做成正式的接口约束。

怎么做：原文分三层讲。下图按当前源码整理（本页归纳）。− 表示原文提到、当前代码已没有，~ 表示与原文说法不同。

Codex 的风险控制接口本页归纳，按当前源码
  • 工具 schema
    • exec_command只有 cmd 必填；另有 workdir、shell、tty、yield_time_ms、max_output_tokens、login
    • −shell、shell_command原文说它们要求设 workdir、提醒别滥用 cd
  • 审批参数
    • sandbox_permissionsuse_default 或 require_escalated；开关打开时还有 with_additional_permissions
    • justification申请提权时给用户看的问题
    • prefix_rule建议一条可复用的放行前缀
    • ~request_permissions 工具单独申请网络和文件权限；开关默认关闭
  • 策略引擎 execpolicy
    • 规则语言prefix_rule、network_rule、host_executable
    • 评估Policy、Rule、Evaluation、Decision、PolicyParser
    • 改写入口blocking_append_allow_prefix_rule、blocking_append_network_rule
−1 删除 ~1 修改
  • 工具 schema：exec_command 不是收一个命令字符串了事，参数都有名字和说明。原文说，正确的用法被嵌进了工具定义本身。
  • 审批参数：审批和权限提升抽成显式参数，request_permissions 做成单独的工具。
  • 策略引擎：execpolicy 单独做成 crate。原文说，Policy、Rule、Evaluation、Decision、parser 这套命名，说明执行边界已经是一门小型政策语言，不只是几个 if/else。
  • 不是虚张：schema 的必填字段明确，additional_properties 关闭。execpolicy 还导出两个改写函数，所以 Codex 不只检查政策，也准备了修改和补丁的正式入口。

为什么：把规则做成接口和语言，规则就能被单独读、单独改。

事实核对
  • shell 和 shell_command 已不是工具。exec_command 的 workdir 说明只写 “Defaults to the turn cwd”，不要求必须设，也没有提醒 cd。“用法嵌进工具定义”这个论点仍有别的依据。在 Windows 上，exec_command 说明里带一段安全规则，例如递归删除前先核对目标路径。
  • request_permissions 确实是单独的工具，但它的功能开关处在开发阶段，默认关闭。
  • schema 里确实写了 additionalProperties: false，但工具同时标着 strict: false。Codex 解析 exec_command 参数时不拒绝多余字段，所以“阻止模型乱塞参数”不由 Codex 保证。
  • 两个改写函数成立：它们往规则文件追加一行规则。用户批准“以后同类命令都放行”时，core 调用它们。
  • “小型政策语言”成立，但范围要限定。规则文件用 Starlark 语法。README 写明当前只覆盖 prefix rule 子集，“a richer language will follow”。

4.4 运行时审批对照策略语言

做什么：原文把两边的风险闸门放在一起比。

Claude Code：运行时审批链 Codex：显式策略语言和参数化审批
怎样判定 ask / allow / deny 与调用现场紧密耦合，按上下文、工具类型、用户动作和会话状态决定 exec policy 把规则抽离出来，可以单独解析和评估
长处 灵敏 可读性和可迁移性更强，适合团队治理
短处 规则容易藏在运行时逻辑里 系统更重，policy 设计必须当正事维护

原文的说法是：前者像“值班经理现场拍板”，后者像“公司先写好制度，再看这单是否合规”。

事实核对
  • Claude Code 的规则不只藏在运行时里。allow / ask / deny 规则写在 settings.json，有固定语法，例如 Bash(git push *)。三类规则按 deny → ask → allow 的顺序生效。
  • 确实留在运行时里的，是内置判断：只读命令清单、包装命令剥离、auto mode 分类器。文档写明包装命令清单 “is built in and is not configurable”。
  • Codex 也不只靠策略语言。没有规则命中时，由启发式兜底：危险命令检查、审批策略和沙箱类型。运行时还有编排器和并行锁：能并行的工具共享读锁，其他工具独占写锁。
  • 两边都有参数化的提权：Codex 是 sandbox_permissions: "require_escalated"，Claude Code 的 Bash 工具是 dangerouslyDisableSandbox。
  • 仍然成立的差别：Codex 的规则是一门语言，放在独立 crate 里。规则可以附带 match / not_match 例子，加载时自动校验；还能用 codex execpolicy check 单独检查命令。

事实核对

4.5 沙箱与审批：产品定义问题

做什么：原文说，沙箱、审批、权限不是安全附属件。对 coding agent 来说，它们定义了产品是什么。

怎么做：系统若允许模型在用户目录直接跑任意命令，就把风险转嫁给了用户。反过来，能显式表达下面这些边界，才是同时交付能力和行为边界。原文的两种做法：

  • Codex：把 turn 级条件暴露在 thread.ts 里，当作线程语义。
  • Claude Code：把边界压到运行时现场：工具执行、中断、permission hook 和 Bash 限制。

原文的概括是：一个“边做边看守”，一个“先给出执行契约再开始做”。下表核对原文列出的六项边界，各自在哪里表达。

原文列出的边界 Codex Claude Code
sandbox mode ✓thread.ts 的 sandboxMode：read-only、workspace-write、danger-full-access settings 的 sandbox.enabled。沙箱只管 Bash、PowerShell、Monitor 的命令，默认关闭
network access ✓thread.ts 的 networkAccessEnabled sandbox.network.allowedDomains 和 deniedDomains
approval policy ✓thread.ts 的 approvalPolicy 权限模式 permissions.defaultMode，加上 allow / ask / deny 规则
additional directories ✓thread.ts 的 additionalDirectories permissions.additionalDirectories，或 --add-dir
state DB 位置 !不在 thread.ts，是 config.toml 的 sqlite_home 原文没有对应说法
MCP tool approvals !不在 thread.ts，是每个 MCP 工具的 approval_mode 配置 mcp__server__tool 形式的权限规则

为什么：原文认为，能力和边界要一起交付，用户才不必替模型承担风险。

事实核对
  • thread.ts 每次运行都把这些线程选项传给 codex exec。state DB 位置和 MCP 工具审批不在 thread.ts 里，而在 config.toml 里。
  • Claude Code 也把这些边界写成配置，见上表右列。所以“边做边看守”和“先给执行契约”，只能理解为侧重点不同，不是有无之分。
  • Codex 会把契约写给模型：它有按 sandbox_mode 和审批策略选用的说明模板，例如告诉模型 “sandbox_mode is workspace-write”。
  • 同一来源内部不一致：SDK 的审批类型仍列出 on-failure；Rust 代码里 on-failure 只是 on-request 的别名。

4.6 MCP、扩展工具与边界外移

做什么：两套系统都能接外部能力。原文说，差异仍在：扩展能力怎样服从总规则。

怎么做：

Claude Code Codex
原文的概括 skill、hook、permission、工具 prompt 拼成场景化治理链，本地规则跟着现场进主循环 外部能力统一纳入工具系统，是 schema 化的工具对象，不是临时约定
原文的依据 未给源码 tools/src/lib.rs 的 MCP resource、dynamic tool、tool discovery
MCP 工具（核对补充） 名为 mcp__server__tool，受同一套权限规则和 hook 管 转成 Responses API 工具；每个工具可配审批模式
按需发现（核对补充） tool search 默认开启，先只加载工具名 tool_search 和 tool discovery

为什么：原文说，生态一旦变大，“扩展能力如何服从总规则”就成了压舱石。谁先想清楚边界外移，谁的扩展体系就不会变成杂物间。

事实核对
  • tools/src/lib.rs 确实导出 MCP 工具、动态工具和工具发现的类型与转换函数。但 MCP resource 的三个工具定义在 core 的 mcp_resource_spec.rs，不在 tools crate。
  • Claude Code 的扩展也纳入了工具系统：MCP 工具和内置工具用同一种规则格式，skill 也通过 Skill 工具运行。所以两边都把扩展做成了工具对象，原文的对比只能理解为侧重点不同。

4.7 本章结论

原文的结论，单独成节

Claude Code 的工具治理更强地依赖运行时编排与现场审批，Codex 的工具治理更强地依赖 schema、参数化权限和独立策略系统。

原文的比方：前者像经验丰富的工头；后者像施工单位，有制度处和法务部。只看“都能跑命令”，就会错过真正重要的差异：谁在工具动手之前拥有最终秩序。

证据（已按事实修正）

  • 独立策略系统：成立。execpolicy 是单独的 crate，有规则语言、检查命令和改写入口（4.3）。
  • schema：成立，但力度要降。schema 写了必填字段和 additionalProperties: false，但 Codex 解析时不拒绝多余字段（参数阈值表）。
