B

3.1 代理系统的核心是连续性

把代理系统当成“多轮聊天”，会掩盖真正的架构难题。原文认为，代理系统真正难的是连续性，它要回答下面这些问题：

连续性要回答的问题
  • 上一轮做了什么，这一轮怎么接
  • 工具结果怎么回填
  • 中断之后怎么收口
  • 上下文过长时怎么整理
  • 失败时重试，还是忠实汇报

这些问题决定一个系统是不是 agent，而不只是“支持工具调用的问答接口”。原文认为，两者在这里的差异，比任何功能对照都更有含金量。

C

3.2 Claude Code：把连续性压进主循环

做什么：原文说，Claude Code 的主轴在 query() 和 queryLoop() 一带，连续性主要由 loop 维护。

怎么做：关键问题都压进循环状态里，真实的麻烦也在 loop 里处理。

queryLoop原文描述的主循环
循环状态
  • 当前消息序列
  • tool use context
  • compact 跟踪
  • output token 恢复计数
  • pending summary
  • turn count
  • transition
在 loop 里处理的麻烦
  • 工具返回顺序
  • 输出截断
  • prompt too long
  • history snip
  • microcompact
  • 用户插话

为什么这样设计：原文认为，Claude Code 对“代理如何活着”的回答是运行时性的。它的骨架像一台不断自我校正的会话发动机。它不是先建强外部状态模型、再驱动执行。真实的麻烦都发生在 loop 里，所以它把这些麻烦当作 loop 内部的合法状态，不回避。原文的评价是：有工程的粗粝感，不优雅，但通常更稳。

事实核对
  • query()、queryLoop() 和循环状态的各项无法核对，Claude Code 源码不公开（附录第 1 条）。
  • 文档能对上的有：输出超限报错、上下文超限时自动压缩、运行中排队发消息、按 Esc 中断（附录第 2 条）。工具返回顺序、history snip、microcompact，文档没写（附录第 3 条）。
  • 连续性并不只靠 loop：Claude Code 把每条消息、工具调用和结果写进本地 JSONL 会话文件，可以按会话 ID 恢复（附录第 9 条）。
D

3.3 Codex：把连续性拆成线程、rollout 与状态桥

做什么：Codex 更“账本化”。在 core/src/lib.rs 里，连续性分摊到 codex_thread、thread_manager、rollout、state_db_bridge、state 几个模块。原文还列了 message_history，当前 core 里已经没有。

怎么做：在 TypeScript SDK 里，thread 是外部开发者能直接操作的一级概念。Thread 持有 id，可以调用 run() 或 runStreamed()。

原文在这一节配了第二张图，画 Codex 线程一次 turn 的生命周期和记录去向。下图按当前源码重画：+ 表示补上，− 表示与代码不符，~ 表示节点有改动。

  • 线程选项包括 approval policy、working directory、sandbox mode、network access、additional directories，创建线程时设定。每次 turn 都把它们显式交给 exec。
  • 原图注释写：turn 范围内的条件随线程走，不随 prompt 走；线程是可寻址的连续性单位。这和代码一致（附录第 28 条）。
  • thread 不是外围包装，而是执行语义真正经过的一层。

为什么这样设计：连续性不再只是“循环还在继续”，而是“一个线程被一套显式状态结构持续记录和约束”。rollout 的存在说明 Codex 在乎回放、索引、持久化和会话外可见性。原文认为，系统因此更接近执行记录器，而不是现场对话管理器。

事实核对
  • 原文说这些条件是 turn 级参数。实际它们在 ThreadOptions 里，创建线程时设定；turn 级选项只有 output schema 和取消信号等（附录第 14 条）。
  • SDK 每次 run 都启动一个新的 codex exec 进程，靠 resume <threadId> 接上同一线程。这支持原文“线程是一级概念”的论点（附录第 15 条）。
  • 原图把 SDK 事件直接连到持久化组件。实际 SDK 只解析事件，记录由 codex exec 进程内的 core 写入（附录第 25 条）。
  • 原文和原图都是先分离输入、再准备 schema 文件，当前代码相反；turn.completed 也只带 usage（附录第 13、26 条）。
  • 原图里 ThreadManager 到 RolloutRecorder 的连线无法核对，照原图保留。

3.4 差别在于状态安放的位置

Claude Code 当然有状态，Codex 当然有循环。差异不在有没有，而在主权在哪。

Claude Code Codex
状态主权交给 query loop thread 和 rollout 结构
怎样看连续性 “会话怎么继续”是 runtime 的核心问题，许多事情在 loop 里直接解决 连续性不是内部控制流的副产物，而是由线程和状态基础设施承接的显式事实
在用户心智中的位置 query loop 像发动机室，重要，但不一定是用户心智模型的中心 Thread 在 TypeScript SDK 里已是产品概念，开发者直接围绕它思考 agent turn
事实核对

Claude 的 Agent SDK 也有会话 ID，可以用 continue、resume、fork 接上之前的会话。差别在入口：Claude 的 SDK 入口是 query() 函数，会话是它的选项；Codex 的 SDK 入口是 Thread 对象（附录第 11 条）。

3.5 对恢复与可审计性的影响

状态安放的位置，直接影响恢复和审计。

Claude Code Codex
恢复强项 离现场近：很多问题在 loop 内部发现和修复，不必先搬到更高一层的状态模型里再考虑回滚 状态可追踪：线程有 ID，rollout 有记录，state bridge 提供更清楚的外部结构
例子 reactive compact、token 上限恢复、工具中断处理 更容易回答“上一轮到底发生了什么”
原文的概括 现场救火队，擅长维持运行 带档案系统的调度中心，擅长说清楚运行是怎样被维持的

原文还指出 Codex 的“档案意识”：core/src/lib.rs 不只暴露 CodexThread，还在根模块出口附近导出 ThreadManager 和 RolloutRecorder。原文认为，这等于承认连续性不是 loop 的副产品，而是基础设施本身。

事实核对
  • 原文说 lib.rs 还导出 state_db_bridge 和 message_history。实际 state_db_bridge 是 crate 内部模块，只导出 StateDbHandle 和 init_state_db；message_history 不在 core 里（附录第 12 条）。
  • 原文没有提 Claude Code 的会话文件。Claude Code 同样逐条记录消息和工具结果，用于回退、恢复和分叉（附录第 9 条）。所以“说清楚上一轮发生了什么”不是 Codex 独有；差别在 Codex 把线程和 rollout 做成了对外接口（本页判断）。

3.6 对产品和团队接口的影响

主权在 loop（Claude Code） 主权在线程和状态结构（Codex）
团队沿什么组织工作 运行时问题 接口与治理
典型问题 哪些错误需要恢复；哪些动作应当中断；compact 何时触发；工具结果怎样串回主对话 thread 的生命周期；rollout 保留哪些事件；状态库放在哪；approval policy 怎样成为 turn 级选项
路径 先把 agent 做会，再嵌制度 先立制度接口，再让 agent 在里面工作

这一节是原文的观点。其中一处事实要注意：Codex SDK 里的 approval policy 是线程级选项，不是 turn 级（附录第 14 条）。

3.7 本章结论

原文结尾总结
原文结论

Claude Code 的连续性更多由 query loop 承担，Codex 的连续性更多由 thread、rollout 与 state 基础设施承担。前者强调 runtime heartbeat，后者强调 persisted session substrate。

证据（来自本章前文，按事实修正后）：

  • Claude Code：输出超限、上下文超限、用户插话都在运行中处理（3.2）。它同样把会话写进本地文件，可以按会话 ID 恢复（3.2、3.4）。
  • Codex：连续性分摊到 codex_thread、thread_manager、rollout、state_db_bridge 等模块。SDK 的入口是 Thread 对象，每次 run 都靠 thread id 接上同一线程（3.3）。
  • 故障矩阵：原文 10 格里，4 格成立或基本成立，2 格与事实不符。其余 4 格无法核对、只能部分核对，或文档未提（3.4）。

原文提炼的原则：这不是审美差异，而是系统权力分配。谁来拥有连续性，谁就定义了 harness 的中心。

核对结论（本页判断）：Codex 一侧的主线有依据。Claude Code 一侧，原文把它写成“loop 状态容易丢”，不符合文档。两者都持久化会话，差别更接近：Codex 把线程和 rollout 做成对外的一级接口；Claude Code 以 query() 为入口，会话是它的选项。
