# claude_src

这个目录放源码分析类文章的解读页，例如 How Claude Code Works 的 source 系列（示例：[Daemon 与 Bridge 系统深度分析](https://jwangkun.github.io/how-claude-code-works/source/daemon-bridge-deep)）。这类文章按源码文件讲 Claude Code 的实现，正文里有大量代码片段和 Mermaid 图。

本目录的目标是把文章的逻辑讲清楚，不核对文章说得对不对。读者的计算机基础较弱，页面要通俗易懂：生词用白话讲清，整体仍要简洁，不能啰嗦。

## 和上级 CLAUDE.md 的关系

上级 `claudeAnalysis/CLAUDE.md` 的规则在这里照常适用，但“以事实为准”整节不适用。具体改动：

- **以原文为准**：文章说的源码文件、函数名、类型名、数值和流程，都照原文写。不用官方文档核对原文，不做观察和实测，不看任何源码（包括泄露的源码），也不标“事实核对”“无法核对”。讲用户视角时可以查官方文档，见下面“白话讲解”。
- **开头结论**：一句话结论只概括原文的结论，不写“核对后是否成立”。
- **导语**：写原文链接、原文查阅日期，再写一句“正文按原文解读，没有核对源码，也不用官方文档核对原文”。用了官方文档讲用户视角时，写明文档的查阅日期。
- **附录**：不加“附录：事实核对”。
- **原文的图**：按原图重画，不用 `+` `-` `~` 变更标记。
- **代码**：上级规则里“正文删掉代码片段”，在本目录改为下面“代码怎样讲”一节。

上级规则里这几条仍然要特别注意：

- 沿用原文章节结构；保留原文的论点、名词、例子、表格和数值。
- 不加原文没有的例子和背景知识。例外只有两种：用户视角的说明（取自官方文档），和术语的一句话定义。做法见“白话讲解”。
- 原文前后矛盾时，在页面上指出，不擅自统一。正文、代码和图三者对不上也算。例如示例文章的图里，PID 文件叫 `session_{pid}.json`；正文和文件名正则写的是 `{pid}.json`。
- 自己做的归类和示意图，标“本页归纳”或“示意”。
- 正文不能比原文复杂。一段代码换成一张图或一张表，不要图、表、代码三样都给。

## 讲清逻辑

- 每节讲清三件事：这部分做什么、怎么做、为什么这样设计。“为什么”只写原文给出的理由；原文没说的，不替它补。
- 先给结构，再讲细节。一节涉及几个组件时，先用一张图交代组件和它们的关系，再逐个讲。
- 同一条逻辑在原文里分散在几处时（例如一处讲轮询循环，一处讲退避参数），可以在讲到它的那一节串起来，并注明出自原文哪几节。
- 原文只给代码、没用文字解释的地方，从代码读出它在做什么，用文字和图说出来。只写代码里写明的内容：不推测代码没写的分支，也不补全 `// ...` 省略的部分。

## 白话讲解

白话的作用是帮读者看懂生词，不是把正文再讲一遍。加了白话，页面可以比原文长一点，但不能更难读，也不能变散。

白话放在三处，各管一件事：

| 位置 | 写什么 | 篇幅 |
|---|---|---|
| 开头一节“先看懂” | 先讲文章里的功能在用户眼里是什么、怎么用，再给原文的全局结构，最后集中解释全篇反复出现的基础词 | 用户视角配一张示意图；基础词不超过 8 个，每个一两句 |
| 每节开头的 `> **白话**：` | 这一节在做什么，以及读懂这一节必须先懂的词 | 2 到 4 句，或不超过 4 项的短列表 |
| 文末“附录：名词表（白话）” | 其余名词，按类别排，例如进程与系统、网络与通信、身份与安全、开发与发布、本系统自己的名词；注明出现在哪几节 | 每个一句 |

不啰嗦：

- 一个词只认真解释一次。开头一节讲过的基础词，后面不再解释，名词表也不收。每节白话讲过的词，名词表里只收同样短的一句，方便查找。
- 白话不复述正文。正文已经说清楚、也没有生词的节，不加白话。
- 术语只写它是什么、在本文里起什么作用，不扩展用法、历史和变体。
- 不为了通俗加原文没有的例子或场景。直接讲机制，不用生硬类比。
- 句子要短，一句只说一件事。能用短列表说清的，不写成长段。
- “为什么这样设计”仍只写原文给的理由，白话里也不替原文补。

用户视角可以查官方文档：

- 开头一节讲“用户怎么用”时，可以查 code.claude.com/docs，内容标“官方文档”。它只帮助理解，不算核对原文，也不标“事实核对”。
- 官方文档的内容集中放在开头一节；正文里最多在个别地方加一两句，同样标“官方文档”。
- 原文和官方文档的命名或命令对不上时（例如原文写 `claude ps`，文档写 `claude agents`），在开头一节用一个提示框把两种说法并列写出。不判断谁对，只提醒读者自己动手时按文档的命令来。正文照原文写。

示例：`Daemon-与-Bridge-系统深度分析.html` 是第一个按这个做法改的页面。

## 代码怎样讲

文章里的代码是原文内容，要讲清，但不在页面上大段照贴。每段代码先判断它要说明什么，再选形式：

| 代码在说明什么 | 怎样讲 |
|---|---|
| 控制流：循环、分支、重试、退避 | flow 图。循环画回边，分支写条件 |
| 多方交互：请求顺序、协议、注册和连接步骤 | sequence 图 |
| 判断函数：返回 true / false 的条件 | 判断 flow，或一张 ok / no 表 |
| 类型和数据结构 | 按用途分组的 tree 或表，不逐字段照抄；原文解释过的字段保留解释 |
| 函数签名 | 不画图。一句话说清它接收什么、返回什么、在流程里处在哪一步 |
| 生命周期：创建、运行、清理 | flow 或 timeline，按先后写出每一步由哪个函数做 |
| 数值和阈值：间隔、超时、上限 | 表格，保留原文的数值和单位 |
| 只说明一个路径或常量 | 一句话写出结论，不画图 |

- 图放在原文代码所在的位置。图前写一句“下图据原文 `<文件>` 中 `<函数>` 的代码绘制”。
- 节点写这一步做什么。函数名只写在入口和关键节点上。
- 删掉行号（如 `bridgeMain.ts:600`）。文件名和函数名在它是这一节入口时提一次。
- 判断条件本身就是要点、且不超过 15 行时，可以在图旁保留原文代码，代码块标题写“原文代码 · <文件>”。不要只贴代码不画图。
- 图只画代码和正文写明的步骤。代码里用 `// ...` 省略的部分，图上也写成省略。

## 原文的图

- 这类站点（VitePress）的 Mermaid 图在浏览器里渲染。下载的 HTML 里只有“加载图表中...”占位，列 `<img>` 和 `<svg>` 找不到它们。
- 图的源码在页面对应的 JS 文件里：
  1. 从 HTML 里找到 `assets/<页面路径>.md.<hash>.lean.js`。
  2. 下载去掉 `.lean` 的完整版。
  3. 文件里每张图是 `diagram:"<base64>"`，解码后就是 Mermaid 源码。
- 代码块在 HTML 的 `<pre>` 里。
- 记下每张图在哪一节、占位符前后是哪段文字，按原位置放回。
- 用 am 的 flow、sequence 或 tree 重画，保留原图的节点和分组（Mermaid 的 subgraph 对应 `group`）。原图节点里的路径和函数名照写。
- 原图和正文或代码对不上时，图照原图画，在图下指出不一致的地方。

## 结构

- frontmatter：`template: doc`；`source:` 写原文完整 URL。
- 导语：`原文：[标题](完整 URL)`、一句话结论、“正文按原文解读”的说明、查阅日期。
- 开头一节是“先看懂”，标 `{meta="本页补充"}`，写法见“白话讲解”。
- 正文按原文章节，每节标 `{meta="原文 1.2"}`。原文的“总结”单独成节，放在正文最后。
- 总结之后是“附录：名词表（白话）”。其他附录（如试点审核用的代码去向表）放在它后面。

## 制作页面

- 页面 `-o` 到本目录（`claude_src/`），文件名用原文标题。
- 其余做法沿用上级规则：curl 加 `--ssl-no-revoke`；下载的网页放进新的空临时目录；草稿写进临时文件再渲染；修改时用 `am render <草稿> -o <原页面路径>` 原地覆盖。
