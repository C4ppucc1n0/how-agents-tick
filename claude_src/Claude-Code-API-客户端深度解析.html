原文：Claude Code API 客户端深度解析

一句话结论（本页概括原文）：原文认为，Claude Code 的 API 客户端分四层：对外入口、queryModel 核心、withRetry 重试、getAnthropicClient 客户端工厂。它用生成器边运行边推送结果，再用重试、降级、看门狗和缓存守卫，应对出错、卡顿和花费。

  • 做什么：把对话整理成 API 请求，发给 Anthropic 或云厂商的模型服务。再把流式传回的回答拼成消息，同时记下用量和花费。
  • 怎么做：按环境变量选 Provider；出错时退避重试、换备用模型或改用非流式请求；用看门狗发现卡住的连接；用缓存标记和会话内锁定保住缓存。

白话地说（本页归纳）：你每发一条消息，Claude Code 都要把整段对话打包，发给模型服务，再一段段收回回答。这篇讲的就是“打包、发送、收回、出错重来”这一套。

Streaming 实现：SSE 事件解析

原文 4.1–4.7

白话：

  • 看门狗：一个定时器。每收到数据就重置，太久没被重置，就判定连接卡住了。
  • O(n²)：工作量随数据长度的平方增长。数据长一倍，工作量变成四倍。

入口和发起请求

对外有两个入口（原文 4.1）。queryModelWithoutStreaming 一次返回完整的 AssistantMessage；queryModelWithStreaming 是生成器，边收边交出流事件、助手消息和 API 错误消息。两者最终都调用内部的 queryModel() 生成器。

原文 4.2 说，这里有一个重要的实现决策：用 SDK 的原始 Stream，不用 BetaMessageStream。

  • 为什么：原文注释说，这样可以避免 O(n²) 的 partial JSON 解析。
  • 怎么做：调用 anthropic.beta.messages.create，带上 stream: true 和取消信号 signal，再接 .withResponse()。
  • .withResponse() 的作用：同时拿到 request_id 和原始 Response 对象。后面的超时、取消、配额提取都要用到它们。

非 Streaming 降级

Streaming 失败时（超时、空流等），自动改用非 Streaming 请求，由 executeNonStreamingRequest() 发出（原文 4.7）。设环境变量 CLAUDE_CODE_DISABLE_NONSTREAMING_FALLBACK 可以关掉这一降级。

降级后的请求有几处调整：

项目 非 Streaming 时
max_tokens 取原值和 MAX_NON_STREAMING_TOKENS（64,000）中较小的
thinking 预算 开了 thinking 时，预算不超过新的 max_tokens 减 1
超时 设了 API_TIMEOUT_MS 就用它；否则远程环境（CLAUDE_CODE_REMOTE）120 秒，本地 300 秒
529 计数 Streaming 的错误是 529 时，连续 529 计数从 1 开始，否则从 0 开始

完整的降级时序见 N 节 13.3。

F

重试逻辑与错误处理

原文 5.1–5.9

白话：出错后不马上重发，先等一会儿。指数退避指每次等待的时间翻倍。本节还有两种“换个方式继续”：换备用模型，和 Fast Mode 降回标准速度。

withRetry：生成器式的重试

withRetry.ts 用生成器实现重试（原文 5.1）。它接收三样东西：造客户端的函数 getClient、真正发请求的函数 operation、重试选项。

它的返回类型是 AsyncGenerator<SystemAPIErrorMessage, T>，意思是：

  • yield：重试等待期间发出 SystemAPIErrorMessage，让界面显示重试消息。
  • return：成功时返回操作结果。

重试过程中要改的状态放在 RetryContext 里（原文 5.2）：model、thinkingConfig、fastMode（5.7 用），以及上下文溢出时自动调整的 maxTokensOverride（5.9 用）。

两种自定义错误（原文 5.3）：

错误 含义 带的信息
CannotRetryError 不能再重试了，已用完所有尝试 原始错误、RetryContext
FallbackTriggeredError 模型降级信号，3 次 529 后触发 原模型、备用模型
