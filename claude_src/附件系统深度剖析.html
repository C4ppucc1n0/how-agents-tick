一句话结论：原文认为，附件系统是一个高度模块化、容错性强的上下文收集框架。它是 Claude Code 处理复杂长会话的关键基础设施。

  • 做什么：每次用户发送输入或工具循环再走一轮，收集、验证、转换各种上下文片段，作为附件注入对话。

附件处理架构

原文 1.1–1.3

白话：一个总入口 getAttachments() 调用一批附件生成器，每个生成器只产出一类附件。生成器分三组，按规定的先后跑。某一个出错或超时，只丢掉它自己那份。

整体架构

原文说，附件系统的设计遵循“工厂模式 + 策略模式”。getAttachments() 是统一入口，内部用 maybe() 函数包装多个独立的附件生成器。每个生成器负责一类特定附件。

I

附件存储与清理

原文 7.1–7.3

白话：附件只放在内存（RAM）里，不写到磁盘。要清理的有两样：缓存 readFileState，它记着读过哪些文件；还有已经送达的异步 Hook 结果。LRU 是一种淘汰规则：缓存满了，就丢掉最久没用过的那条。

内存中附件

原文说，附件本身不持久化到磁盘。Attachment 对象作为消息数组的一部分存在内存里，随消息数组的压缩（compaction）或会话结束而释放。

本页补充：同站另一篇的说法

本站《会话存储系统深度分析》的条目类型表，把 attachment（附件消息）列为“始终写入”会话文件。两篇说法不同，本页照这一篇写。

文件状态缓存清理

readFileState 是 100 条的 LRU 缓存，跟踪所有已读取的文件内容。原文列的三条清理策略：

策略 做法
LRU 淘汰 缓存满时，淘汰最久未使用的文件状态
文件删除清理 文件被删除时从缓存中移除。代码在文件变更检测里：读到 ENOENT（文件不存在）错误，就删掉缓存记录，返回 null
Compact 重置 上下文压缩后，旧附件从消息数组中移除，但 readFileState 保留

异步响应清理

异步 Hook 的响应转换成附件以后，removeDeliveredAsyncHooks() 按进程 ID 把它们从注册表中移除。

空文件和损坏文件处理

  • 空图片：图片数据为 0 字节时，抛出 ImageResizeError（“Image file is empty (0 bytes)”）。
  • 大数据文件：触发截断读取。readTruncatedFile() 再调一次 FileReadTool.call()：从 offset 开始（没给就从第 1 行），最多读 MAX_LINES_TO_READ 行。返回的 file 附件标 truncated: true。

特殊模式下的跳过

简单模式（CLAUDE_CODE_SIMPLE）或无附件模式（CLAUDE_CODE_DISABLE_ATTACHMENTS）下，大部分附件生成被跳过。两个环境变量任一为真，就只返回 getQueuedCommandAttachments() 生成的队列命令附件。
