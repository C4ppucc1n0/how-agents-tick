自己动手时按文档：原文和文档写法不同的几处

下面只把两种说法并列，不判断谁对。正文照原文写。

  • 清单文件：原文的图里叫 manifest.json，类型定义在 schemas.ts。文档写的是插件目录里的 .claude-plugin/plugin.json。

  • 官方市场的信任：原文说官方市场的插件完全信任，不弹警告。文档说不管来自哪一级市场，装上的插件都能用你的用户权限运行代码，安装前要先审查。

插件清单格式

原文 2

白话：zip 包是把一堆文件压成一个文件。清单就是插件的“自我介绍”。

插件有两种分发形式：.mcpb 文件（MCP Bundle，一个 zip 包），或一个目录。清单的类型 PluginManifest 定义在 src/utils/plugins/schemas.ts。下表按用途分组（本页归纳），括号里是原文注释：

用途 字段
必填 name、description、version
可选的元数据 icon、author、license、homepage、repository
命令 commands（命令 .md 文件路径）、commandsPaths（额外命令目录）、commandsMetadata（命令元数据，见 E 节）
技能 skills（技能的名字或选择器）、skillsPaths（额外的技能目录）
钩子和 MCP hooks、mcpServers
配置和限制 userConfig（让用户填的配置项）、requires（依赖的插件 ID）、platform（平台限制：darwin、win32、linux）

内置插件的定义

内置插件不用清单文件，而是用 TypeScript 定义，类型是 BuiltinPluginDefinition。它和清单的不同之处：

字段 原文的说明
name、description、version 和清单一样
defaultEnabled 是否默认启用，默认为 true
isAvailable() 按平台或生命周期决定这个插件能不能用
skills 内置技能的定义（BundledSkillDefinition），不是路径
hooks、mcpServers 钩子设置和 MCP 服务器配置

原文 3.1–3.3

发现：插件从哪来

启动时，Claude Code 从下面几种来源发现插件（原文 3.1）：

来源 从哪来 说明
官方市场（Official Marketplace） 托管在 api.anthropic.com/mcp-registry/ 拉取后缓存在本地；由 marketplaceManager.ts 负责搜索
内置（Built-in Commands） 编译进 CLI 程序，位于 src/plugins/builtin/ 除非明确禁用，否则始终可用
内联插件（Inline Plugins） 启动参数 --plugin-dir /path/to/plugin 直接从文件系统加载
已安装插件（Installed Plugins） 之前从市场安装，存在 ~/.claude/plugins/ 有缓存，离线也能用
企业管理的插件（Managed Plugins） 由企业策略管理 由 managedPlugins.ts 强制执行

用途 字段

信任校验

来自市场的插件要经过信任校验。安装前，PluginTrustWarning 组件（src/commands/plugin/PluginTrustWarning.tsx）显示信任信息（原文 3.3）。信任分四级：

来源 信任级别 用户看到什么
官方 Anthropic 市场 完全信任 自动安装，不警告
用户添加的市场 中等信任 第一次从这个市场安装时警告
本地目录、--plugin-dir 中等信任 警告；路径是用户自己选的
黑名单里的插件 不信任 拒绝加载，显示错误

黑名单由 pluginBlocklist.ts 管理，可以通过企业策略远程更新。H 节 6.1 对这四级有更细的说明。

/reload-plugins 命令

/reload-plugins（src/commands/reload-plugins/）在运行中刷新插件，不用重启 CLI（原文 4.4）。它做这几件事：

插件安全模型

原文 6.1–6.3

白话：

  • 签名验证：检查插件确实出自声称的发布方，中途没被改过。
  • 黑名单（blocklist）：明确禁止的插件 ID 名单。

信任级别

下图据原文 6.1 的文字图重画：

插件的信任级别
官方 Anthropic 市场
  • 签名已验证
  • 自动信任，不弹警告
  • 可以被企业策略屏蔽
第三方市场（用户添加）
  • 不验证签名
  • 第一次安装时显示警告
  • 之后从同一市场安装，每个会话警告一次
本地目录、--plugin-dir
  • 路径由用户明确指定
  • 显示警告，需要用户确认
  • 确认后视为可信
黑名单（pluginBlocklist.ts）
  • 不能安装，也不能加载
  • 显示错误消息，说明原因
原文前后写法不同

3.3 节说，第三方市场只在“第一次从这个市场安装时”警告。6.1 节又说，之后从同一市场安装，每个会话还会警告一次。

策略集成

插件的行为受企业策略约束（原文 6.2）：

文件 作用
pluginOnlyPolicy.ts 打开时，技能和 MCP 只能来自插件；用户自己写的本地技能和 MCP 服务器被拦下
pluginBlocklist.ts 维护黑名单，记录已知恶意或不允许的插件 ID；可以通过策略设置更新
pluginFlagging.ts 标记行为可疑的插件，例如有意料之外的网络请求，或访问文件系统过多

内容安全

插件的命令和技能，和用户自己写的技能遵循同一套安全模型（原文 6.3）：

  • 执行 shell 命令（!`command`）要经过同一套权限系统。
  • ${CLAUDE_PLUGIN_ROOT} 的替换受控制，插件不能读自己目录以外的内容。
  • 发给模型的技能内容里，敏感的用户配置值会被遮住。
  • 插件带来的 MCP 服务器，和手动配置的服务器一样，受允许、拒绝策略约束。

插件、MCP 与内置工具对比

原文 7

原文从九个方面对比三种扩展方式：

方面 插件 MCP 服务器 内置工具
分发 市场、.mcpb、目录 任意 URL 或本地可执行文件 编译进 CLI
能力 命令 + 技能 + 钩子 + MCP 工具 + 资源 + 提示词 单个有类型的函数
信任模型 清单校验 + 市场信誉 服务器 URL 或可执行文件路径 完全信任

和手动配置的去重 按内容签名比较 手动配置的胜出
插件之间去重 和更早加载的插件的服务器重复时，压下这一个 先加载的胜出
策略过滤 和手动配置的服务器用同一套允许、拒绝规则 —
