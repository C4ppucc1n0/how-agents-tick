一句话结论：原文认为，AgentTool 是一个设计精巧的子代理系统，核心理念是递归委派。它提供代理的定义、加载、执行和通信机制，让 Claude Code 能把复杂任务拆成子任务并行处理。

  • 做什么：让主代理按需生成子代理。子代理有自己的系统提示词、工具和对话上下文，独立完成多步任务，再把结果交回。

原文 1–2

白话：递归指子代理还能再派自己的子代理，一层套一层，形成一棵树。

AgentTool 是什么

原文说，AgentTool 是 Claude Code 中最核心的工具之一。它让主代理能动态生成子代理。子代理是一个独立的 Claude Code 实例，有自己的系统提示词、工具集合和对话上下文。

从架构上看，AgentTool 是递归式代理架构的核心支点。主代理通过它生成子代理，子代理还能生成自己的子代理，形成代理树。原文说，这种设计借鉴了人类协作中“分工-委派-汇总”的模式。

代理定义与 AGENTS.md 配置

原文 3.1–3.4

白话：代理定义就是一个子代理的配置：叫什么、什么时候用、能用哪些工具、提示词是什么。联合类型指“几种形状里的一种”。

三种代理定义

所有代理定义都归一成 AgentDefinition 联合类型，有三种（原文 3.1）：

AgentDefinition
BuiltInAgentDefinition内置代理，source 为 built-in；用代码里的 getSystemPrompt 动态生成提示词
CustomAgentDefinition自定义代理，source 为 userSettings、projectSettings、localSettings、policySettings 或 flagSettings；从 AGENTS.md 或 JSON 加载
PluginAgentDefinition插件代理，source 为 plugin；由插件系统注册

共有的字段

所有代理共享 BaseAgentDefinition，共 18 个字段（原文 3.2）。下表的分组是本页归纳，括号里是原文注释：

用途 字段
身份和用途 agentType（代理类型名，唯一标识）、whenToUse（使用场景描述）
工具 tools（允许用哪些工具，* 表示全部）、disallowedTools（禁止用哪些工具）、skills（预加载 Skill）、mcpServers（专属 MCP 服务器）、requiredMcpServers（必需 MCP 服务器名模式）
模型 model（模型别名 sonnet、opus、haiku、inherit）、effort（努力级别）
运行方式 permissionMode（权限模式）、maxTurns（最大轮次）、background（是否强制后台运行）、isolation（隔离模式 worktree 或 remote）
上下文和提示 initialPrompt（首次提示词前置内容）、omitClaudeMd（是否省略 CLAUDE.md）、memory（持久化记忆范围）、hooks（会话钩子）
显示 color（显示颜色）

配置文件格式

用户在 .claude/agents/ 目录下放 Markdown 文件来定义自定义代理。每个文件是一个代理，用 YAML frontmatter 声明元数据（原文 3.3）。原文的示例定义了一个代码审查代理：

字段 示例值
name、description code-reviewer；审查代码改动里的 bug、风格问题和安全隐患
model sonnet
tools、disallowedTools 允许 Read、Glob、Grep、Bash；禁止 Write、Edit
color、maxTurns purple；30
permissionMode、background acceptEdits；false
memory、skills project；my-plugin:lint-check
mcpServers 引用已有的 slack，再内联定义一个 my-custom-server（用 npx 启动）
hooks SubagentStart 时执行 echo "Agent started"
initialPrompt 先关注安全关键路径

frontmatter 之后是正文，原文示例写的是“你是一位代码审查专家...”。

关键约束：

  • name 和 description 必填。
  • 没写 tools，表示允许所有工具；tools: [] 表示不允许任何工具。
  • 加载时按优先级覆盖，见下一小节。

内置代理类型

原文 4.1–4.4

内置代理列表

builtInAgents.ts 里的 getBuiltInAgents() 组装所有内置代理（原文 4.1）：

代理类型 描述 工具 条件
general-purpose 通用代理，处理复杂多步任务 全部工具 始终存在
explore 只读代码搜索，快速定位文件 Read、Glob、Grep、Bash（只读） 受 tengu_amber_stoat 功能开关控制
plan 只读架构规划，设计方案 Read、Glob、Grep、Bash（只读） 受 tengu_amber_stoat 功能开关控制
statusline-setup 状态栏设置向导 受限工具 始终存在
claude-code-guide Claude Code 使用指南 搜索和 Web 工具 非 SDK 入口时
verification 验证代理，尝试破坏性测试 全部工具 受 tengu_hive_evidence 功能开关控制

General-purpose 代理

它是默认的子代理类型，有全部工具权限（tools: ['*']），适合大多数子任务（原文 4.2）。它的系统提示词很短，要点是：完成任务后，给一份简洁的报告，写做了什么和关键发现；调用方会转告用户，所以只要要点。

Explore 和 Plan 代理

这两个代理只读（原文 4.3）：

  • 提示词：开头写明 READ-ONLY MODE，严禁新建、修改、删除文件。
  • 工具：没有 Write、Edit 等写工具，从根本上杜绝改文件。
  • 为什么：原文说，这样主代理可以放心把探索性任务交给它们。
  • 优化：上下文省略 CLAUDE.md 里的提交、PR、Lint 规则（omitClaudeMd: true），也省略 Git 状态信息。原文说每次启动节省约 5-15 Gtok，依据是官方注释，覆盖 34M+ 次 Explore 启动。
原文的数字写法

Gtok 指十亿 token。原文写“每次启动”节省 5-15 Gtok，同一句又说覆盖 34M+ 次启动；15 节也写“每次节省 5-15 Gtok”。原文没有说明这个数是每次的还是合计的。

Verification 代理

验证代理的角色是“尝试破坏实现”，而不是确认工作正常（原文 4.4）。它的系统提示词强调四点：

  • 识别回避验证的做法，例如只读代码、不跑测试。
  • 不被“前 80% 的完成度”迷惑。
  • 按变更类型（前端、后端、CLI、配置等）用不同的验证策略。
  • 识别并克服自己替结果找理由的倾向。

F

Fork 子代理机制

原文 6.1–6.4

白话：

  • Fork：复制当前对话，派出一个“分身”接着做子任务。
  • Prompt Cache：请求开头和之前的请求完全相同时，服务端复用已处理过的部分，更快也更省。
  • 字节一致：逐个字节都相同。差一个字，缓存就用不上。

设计目标

Fork 子代理是 AgentTool 的一个实验特性，由 FORK_SUBAGENT 功能开关控制（原文 6.1）。原文给了三个设计目标：

  • 上下文继承：子代理继承父代理的全部对话上下文和系统提示词，不用重新交代背景。
  • 缓存共享：所有 Fork 子代理的 API 请求前缀字节一致，让 Prompt Cache 命中率最大。
  • 统一交互模型：所有代理都通过“异步后台 + 通知”执行。
